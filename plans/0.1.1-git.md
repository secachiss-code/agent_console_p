## Быстрое возвращение к работе

Цель версии — перейти от «проект → вкладка, владеющая worktree» к
«проект → рабочая сессия задачи → вкладки исполнителей». Сессия сохраняет ветку,
рабочее пространство и историю независимо от закрытия или замены агента.
В базовую ветку проекта интегрируется результат сессии.

Короткое описание для задачи или передачи работы:

> AConsole 0.1.1 «Работа с Git». Ввести рабочие сессии задач, отделённые от
> нативных сессий CLI-агентов. Перенести владение основным worktree, веткой,
> чекпоинтами и финальным merge/cleanup с вкладки на сессию. В общем каталоге
> разрешать одного исполнителя с подтверждённой передачей управления;
> параллельных исполнителей запускать в изолированных worktree и принимать
> их результаты в ветку сессии. Сохранить существующие данные, проверки
> актуальности Git, защитные снимки и восстановление журнала после сбоя.

**Текущая точка:** все пять этапов реализованы. Локальный пакет 0.1.1 собран,
проверен в распакованном виде, в систему не установлен. Итоги тестов, замеров,

## Решения и границы 0.1.1

- Рабочую сессию называть `WorkSession`, идентификатор — `work_session_id`.
  Нативный `agent_session_id` и существующий resume CLI не переименовывать
  и не использовать как идентификатор рабочей сессии.
- Проект содержит несколько сессий; сессия содержит основной workspace
  и любое число вкладок, включая временное отсутствие вкладок.
  Владелец управляемого worktree — сессия, вкладка — исполнитель.
- Сохранить три способа выбора основного workspace: новый управляемый worktree,
  основной checkout, существующий worktree. Импортированные каталоги не удалять.
  Один физический основной workspace не может принадлежать двум активным сессиям.
- Для новых управляемых сессий создавать ветку `ac/s-<slug>-<id>`;
  идентификатор обеспечивает уникальность. Уже существующие ветки не переименовывать.
  Базовую ветку сохранять явно, не считать её автоматически равной `main`.
- Общий workspace работает в режиме эстафеты: только один запущенный исполнитель.
  Переключение вкладки в UI не передаёт право записи. Другой агент запускается
  после остановки предыдущего и подтверждения отсутствия его процессов.
  При невозможности проверить остановку передача блокируется, файлы сохраняются.
  Продолжение диалога использует существующий механизм resume конкретного CLI;
  отсутствие поддержки resume отражается в UI как запуск нового диалога.
- Параллельная работа — отдельный worktree исполнителя от зафиксированного HEAD
  сессии. Его результат сначала интегрируется в сессию, затем сессия — в базу.
- Scope файлов в этой версии не является механизмом изоляции или блокировки.
  Параллельная запись в общий каталог, First-Touch Lock и теневые индексы
  исключены из 0.1.1. Внешние редакторы и процессы пользователя остаются внешними
  писателями; гарантировать их авторство по Git или событиям файловой системы нельзя.
- Выборочная отмена вклада агента через обратный patch, автоматический запуск
  цепочек агентов по DAG и точное авторство каждой строки отложены.
  Связь вкладок и коммитов с существующими узлами плана сохраняется.

## Этапы реализации

### 1. Модель, хранение и контракты

- [x] Ввести `WorkSession`: проект, название, базовая ветка, основной workspace,
  происхождение workspace, состояние `active`/`archived`, время создания/изменения.
  Архивирование запрещает новые записи до явного возобновления; архив сохраняет историю.
- [x] Связать вкладки, операции Git и события истории с рабочей сессией.
  Выделить членство исполнителя и владение workspace; не заменять поле владельца
  первым найденным `tab_at()`. Busy-проверки должны учитывать всех участников.
- [x] Добавить RPC создания, получения, списка, переименования и закрытия сессий,
  передачи управления и интеграции результата исполнителя. Добавить
  `work_session_id` в открытие вкладки и ответы состояния; `actor_tab_id`
  использовать для автора действия, а не владельца каталога.
- [x] Сохранить `project_id` в запросах состояния всего репозитория и проверять
  принадлежность сессии проекту, вкладки сессии и worktree workspace.
  Фильтр вкладки в графе не должен менять контекст владения Git.
- [x] Мигрировать прежние вкладки: один существующий workspace → одна рабочая
  сессия, вкладки с тем же каноническим путём объединять. Сохранить ветки, пути,
  планы, CLI resume и признак `created_here`; не выполнять Git-записи в миграции БД.
  Сохранённые workspace без открытых вкладок также должны быть доступны.
- [x] Старые чекпоинты и журналы оставить читаемыми, принадлежность дополнить
  по сохранённым связям. Неоднозначные старые записи показывать как legacy,
  не присваивать произвольной сессии. Не переносить старые refs автоматически.
- [x] Обновить типизированный клиент, схемы, fake core и версию IPC при изменении
  обязательных контрактов; несовместимые UI/core должны получать явный отказ.

Приёмка: миграция старой БД не меняет файлы/refs; сессия и её вкладки корректно
восстанавливаются после перезапуска. Новые контракты проверяются на принадлежность.

### 2. Жизненный цикл и эстафета

- [x] Перенести создание, удержание и очистку основного worktree в сервис сессий.
  Закрытие вкладки останавливает исполнителя и освобождает его ресурсы,
  но не удаляет основной worktree или ветку сессии.
- [x] Реализовать передачу: заблокировать новые запуски/записи сессии → остановить
  прежнего исполнителя и проверить процессы → снять handoff-чекпоинт → сохранить
  завершение этапа → разрешить запуск следующего. Ошибка оставляет сессию без
  нового исполнителя и с объяснимым состоянием для повторной попытки.
- [x] При старте приложения не восстанавливать право записи по одному статусу
  вкладки: сначала сверить процессы. Журналировать незавершённую передачу.
- [x] Снимать начальный и конечный снимки каждого этапа; хранить исполнителя,
  причину, последовательность, HEAD и ссылку на дерево. Не снимать «финальный»
  снимок во время продолжающейся записи агента.

Приёмка: два исполнителя общего workspace не запускаются одновременно;
закрытие любой вкладки сохраняет задачу; сбой передачи не запускает второго агента.

### 3. Состояние Git, история и восстановление

- [x] Сохранить проектный обзор Git и добавить состояние сессии: основной workspace,
  участники, исполнитель эстафеты, результаты изолированных исполнителей,
  незавершённые операции и базовая ветка.
- [x] Новые снимки писать в `refs/aconsole/sessions/<sid>/checkpoints/<seq>`.
  Метаданные этапов хранить в БД с привязкой к refs. Защитные refs перед rewrite
  и для исходных коммитов squash именовать с уникальным ID операции, чтобы
  повторные операции не перезаписывали единственную возможность восстановления.
- [x] Добавить trailer `AConsole-Session: <id>` к создаваемым приложением коммитам;
  оставить существующие trailers. Финальный squash описывает сессию и её участников,
  не приписывает весь результат последнему агенту. Коммиты внешнего CLI без
  trailers остаются допустимыми, их авторство не выдумывается.
- [x] Показывать diff всей сессии и конкретного этапа между его снимками.
  Суммарный вклад агента — список его этапов, а не обещание независимого patch
  поверх любого последующего состояния. Внешние изменения отмечать как неизвестные.
- [x] Откат сессии в 0.1.1 восстанавливает рабочие файлы выбранного снимка,
  сохраняя HEAD и обычный индекс, как текущие чекпоинты. UI явно объясняет эту
  семантику. Перед откатом остановить всех затрагиваемых исполнителей и сделать
  защитный снимок; ошибки восстановления не скрывать.
- [x] Сохранить OID-кэши, пагинацию графа, отказ устаревшему cursor,
  события `GitStateUpdated` и проверки ожидаемого HEAD/индекса.
  Подписки сессий опираются на общий наблюдатель репозитория, не дублируют его.

Приёмка: история этапов переживает закрытие вкладок и рестарт; зафиксированные
данные отделены от предположений об авторстве; откат сохраняет защитную точку.

### 4. Изолированные исполнители и интеграция

- [x] Создавать временный detached worktree от записанного HEAD сессии.
  Закреплять начальную точку и принятый к review результат служебными refs
  исполнителя; незакоммиченный результат фиксировать снимком после остановки.
- [x] Перед интеграцией показывать preview по конкретным OID источника и цели.
  Основной workspace должен быть без незакоммиченных изменений и текущей
  операции, все его исполнители остановлены. Иначе сохранить результат
  исполнителя и предложить сначала привести основной workspace в порядок.
- [x] Интегрировать через существующие механизмы merge, журнала и подтверждения;
  проверить актуальность preview перед записью. Конфликт оставляет изолированный
  результат доступным, основной workspace не меняется автоматически.
- [x] Удалять временный worktree только после доказанного принятия результата
  или отдельного подтверждения отказа от него. Учитывать dirty и ignored файлы;
  результат удерживать ref независимо от существования вкладки.
- [x] Повторный запрос и восстановление после сбоя не должны повторять успешную
  интеграцию. Состояния журнала связываются с сессией и конкретным результатом.

Приёмка: два изолированных агента работают параллельно; устаревший preview
отклоняется; конфликт и сбой не теряют результат и не перетирают основной каталог.

- [x] Перенести основной Git-экран на контекст сессии, сохранив проектный обзор.

## Проверки и завершение версии

- Модель/миграция: пустая БД, старая БД, несколько вкладок одного workspace,
  сохранённый workspace без вкладок, native resume, legacy checkpoints/operations.
- Эстафета: запуск второго агента, ошибка/неопределённость остановки, фоновые
  процессы, сбой до/после снимка, закрытие последней вкладки, рестарт приложения.
- Git: staged/unstaged/untracked, конфликт, detached/unborn HEAD, нестандартная
  базовая ветка, внешнее изменение HEAD/индекса, хуки, отказ записи журнала.
- Интеграция: два результата от одной базы, продвижение ветки сессии между preview
  и подтверждением, dirty основной workspace, конфликт, повтор запроса, рестарт.
- Сохранность: откат с изменённым индексом, защитный snapshot, исходные коммиты
  после squash, ignored файлы, отказ удаления Git, запрет удаления чужого workspace.
- UI: проект/сессия/вкладка, фильтр этапов, передача управления, блокирующие причины,
  подтверждения, восстановление выбора при обновлении, светлая/тёмная/узкая тема.
- Финальные проверки: `tools/check.sh`, тесты core/contracts/unit/gate/hostrun/smoke
  по README, GUI/UI под Xvfb и smoke собранного пакета. Производительность Git
  сравнить с существующими `test_git_scale.py` и `tools/git_bench.py`.

Базовая проверка при ознакомлении: 100 профильных тестов прошли (59 адаптеров,
worktree, diff и checkpoints; 41 интеграционный тест Git). GUI и нагрузочные
тесты тогда не запускались. В песочнице запрещено создание Unix-сокетов;
интеграционные тесты были успешно повторены с разрешением вне песочницы.
Это исходная проверка 0.1.0, не доказательство готовности будущей 0.1.1.
