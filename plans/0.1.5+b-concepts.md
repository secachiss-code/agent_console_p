# AConsole 0.1.5+b — концепции для плана 0.1.5

**Состояние:** концептуальный источник, не исполняемый граф задач.  
**Срез:** 2026-11-22.  
**Назначение:** собрать проверенные наблюдения и проектные решения, из которых после выбора объёма будет собран исполняемый план выпуска `0.1.5`.

`0.1.5+b` здесь обозначает редакцию концепции. Это не версия пакета и не утверждение, что версия `0.1.5+b` уже выпущена. Текущая версия исходников и пакета в README — `0.1.5+a`.

## Краткий вывод

Для 0.1.5 нужен единый управляемый контур анализа проекта: курируемые языковые пресеты, проверенные расширения и исполняемые инструменты, проектная привязка, окно результатов, а также MCP-доступ к воспроизводимым результатам. Расширения VS Code следует брать готовыми из совместимого реестра, но считать источником диагностики конкретный инструмент, его версию, конфигурацию и снимок проекта. Установка расширения сама по себе не гарантирует, что анализатор правильно видит проект.

До сборки реального плана требуется закрыть два пробела планирования: связанный со мной MCP-набор не предоставляет методов создания/изменения плана; существующий `plan/save` при передаче узлов заменяет весь черновой граф. Концепции и исполняемые узлы нужно хранить и редактировать раздельно.

Также нужен явный механизм выбора целевой рабочей копии. Запись в соседний worktree, контейнер или установленную копию приложения вместо указанного пользователем проекта — ошибка результата, даже если содержимое документа правильное.

## 1. Что показала проверка текущей версии

Эти наблюдения — входные данные для планирования, а не утверждение, что каждая проблема уже воспроизведена отдельным тестом. Полный набор тестов в последней проверке кода не запускался.

### 1.1 Настройки и сборка

- Исправление открытия модального окна настроек просмотрено; дефектов в самом исправлении не найдено. Изменения переводов и проверки локали остаются незакоммиченными в рабочем дереве.
- Сборщик Debian включает содержимое отслеживаемых Git файлов из рабочего дерева, в том числе локальные изменения. Нужен проверяемый источник сборки: чистый коммит или явно зафиксированный tree hash, плюс однозначная версия пакета.
- README содержит противоречивые упоминания версий `0.1.4+f` и `0.1.5+a`. Перед выпуском нужна единая версия в коде, документации, имени пакета и отчёте сборки.

### 1.2 Ruff и Pylint

- Штатный Ruff проекта из конфигурации репозитория сообщил ноль замечаний. Ruff из VSIX в режиме настроек по умолчанию выдал 1 318 сообщений на 705 Python-файлах; часть — ложные срабатывания из-за несовпадения настроек, включая проверку имён при отложенных аннотациях в Python 3.15.
- Полный прогон Pylint из VSIX в контексте исходников выдал 12 744 сообщения: 9 911 convention, 1 206 refactor, 936 warning и 691 error. В числе ошибок были отсутствующие импорты и статические ограничения динамических API; правило длины строки также расходилось с проектным пределом. На отдельных прогонах действовал лимит в 100 результатов.
- Адаптер Pylint указывает `/usr/bin/python3`, тогда как проект требует Python `>=3.15`; хостовый Python был 3.12. Это ломает разбор части исходников и импорты. Анализатор должен использовать интерпретатор и зависимости проекта либо явно сообщать, что достоверная проверка невозможна.
- Ruff и Pylint сейчас используют настройки расширений по умолчанию. Без передачи проектной конфигурации и согласованного окружения результат не эквивалентен штатному запуску проекта. По умолчанию запускать оба как взаимозаменяемые линтеры не следует.

### 1.3 Среда расширений и полнота результатов

- Управляемый VSCodium на этом хосте завершался с ошибкой Electron `chrome-sandbox`: безопасное извлечение архива сняло требуемый setuid с `chrome-sandbox`, а user namespaces недоступны. Для аудита использовался системный Code OSS с теми же изолированными профилями и закреплёнными VSIX. Это обход для проверки, а не исправление поставляемого runtime.
- Текущий extension host работает с правами пользователя ОС. Приватный профиль разделяет настройки и данные, но не изолирует исполняемый код расширения или команды проекта.
- Мост ограничивает выдачу 100 диагностическими сообщениями и помечает ровно 100 результатов как усечённые. Нужны явная полнота и пагинация, чтобы пользователь и модель не приняли частичный отчёт за полный.
- Во время занятости анализатора UI может принять старый статус с признаком занятости за успешное «Обновлено». После успешной повторной операции также может оставаться старый текст ошибки; часть сообщений не локализована.

### 1.4 Остальные замечания полного ревью

- MCP-таблица с лимитом 2 048 сессий может вытеснить ещё активную сессию, а устаревшее состояние не очищается согласованно.
- Запуск ingest не проверяет исключение завершившейся задачи uvicorn; ядро может продолжить работу без ingest.
- При завершении sidecar результат остановки orphan-процессов игнорируется, после чего вкладка отмечается завершённой даже при оставшемся процессе.
- Обработка пользовательского `--socket` меняет права родительского каталога и безусловно удаляет существующий путь. Нужны безопасные проверки владельца, типа и ожидаемого каталога.

Эти пункты требуют первичной сортировки и подтверждения на актуальной ревизии до назначения в исполняемый план. Для каждого принятого пункта зафиксировать уровень риска, сценарий воспроизведения и критерий закрытия.

## 2. Концепция процесса планирования

### Текущее состояние

- В ядре AConsole есть MCP-метод `plan_create`; в приложении также есть IPC/API `plan/create` и `plan/save`.
- Повторный `plan_create` с тем же заголовком проекта возвращает тот же план. `plan/save` при передаче `nodes` заменяет весь набор черновых узлов. В контракте передаются пути, зависимости, условия приёмки и проверки, но нет отдельного типа концепции с источниками, альтернативами и статусом решения.
- В текущем подключении Codex доступны просмотр планов и управление узлами, но отсутствуют MCP-инструменты создания/сохранения плана. Поэтому этот документ можно сохранить в Git, но нельзя честно представить как уже созданную запись PlanBoard. Это конкретный интеграционный пробел, который нужно закрыть до пересборки концепций в исполняемый план.
- План `0.1.4` закрыт и заморожен; `0.1.5+b` в текущем PlanBoard не найден. Старые планы не следует переиспользовать под новый объём.

### Предлагаемая модель

1. **Реестр концепций** хранит цель, наблюдения, источники, предположения, альтернативы, риски, зависимости, статус решения и выбранный вариант. Концепция не является разрешением запускать работу.
2. **Исполняемый граф** создаётся только из выбранных концепций. Каждый узел получает ограниченный объём, точные пути, зависимости, проверяемую приёмку и команду проверки, если она уместна.
3. **Преобразование в план** сохраняет связь узла с исходными концепциями и ревизией документа. Изменение концепции после построения графа должно показывать затронутые узлы.
4. Методы создания/редактирования должны быть доступны оркестратору через MCP. Для добавления или исправления одного концепта нужен инкрементальный метод с `expected_revision`; правка одного узла не должна требовать отправить и заменить весь граф.
5. Операции создания должны быть идемпотентны по идентификатору проекта и версии концепции; обновления — атомарны и обнаруживают конфликт ревизий. История решений, попыток и завершённых узлов не должна теряться при редактировании черновика.

**Открытый выбор для реального плана:** отдельные методы `plan_concept_*` или версионируемый документ концепций внутри существующего plan resource. В любом варианте должны быть чтение, создание, изменение, фиксация решения, сборка исполняемого графа и проверка результата через тот же MCP-контекст проекта.

### Концепция: идентификация целевого проекта и места записи

Рабочая сессия может одновременно видеть основную копию проекта, один или несколько Git worktree, контейнерную копию и установленный пакет. Перед изменением файла, созданием плана, сборкой, установкой или публикацией система должна определить и показать, какой именно объект выбран.

- Контекст операции несёт идентификаторы проекта и worktree, канонический абсолютный корень, Git root/branch/HEAD и признак контейнерной или установленной копии, если это применимо.
- Перед первой записью в операции UI и MCP-результат показывают целевую копию и путь. Если цель неоднозначна или путь не совпадает с заявленным проектом, запись не выполняется до явного выбора.
- Плановая запись и файловый источник плана различаются в интерфейсе. Если PlanBoard хранит граф в базе приложения, интерфейс отдельно сообщает, в каком Git checkout лежит концептуальный Markdown-источник.
- Результат записи возвращает абсолютный путь, идентификатор проекта/worktree и ревизию. После записи приложение повторно читает этот путь и проверяет ожидаемое содержимое/ревизию; сообщение «сохранено» нельзя показывать только по факту успешного IPC/MCP вызова.
- Все команды продолжения используют тот же target identity. Смена worktree или корня в середине операции создаёт новый контекст и требует переоценить цели записи, а не молча перенаправляет их.
- В журнале операции остаются исходная цель, фактическая цель, причина выбора, изменённые файлы и подтверждение чтением после записи. Это помогает понять, куда попали документы, пакеты и результаты анализа.

**Вопросы для решения:** может ли вкладка быть связана только с одним worktree; как представлять зарегистрированный проект при работе через Codex worktree; какие операции допускают межкопийный перенос; как разрешать symlink и контейнерные пути без потери идентичности.

### Концепция: разрешения с настройками по каждому агенту

Сейчас в настройках есть общие параметры запросов разрешения: где показывать запрос, кто решает, как обрабатывать опасные вызовы; также существует переопределение для проекта. Запускатели получают эффективную политику для вкладки, но не отдельную настройку для Cursor, OpenCode и остальных агентов.

Из-за этого общее разрешение `allow` или `deny` может остановить запуск агента, чья автоматическая политика не подтверждена:

- Cursor возвращает `Cursor automatic modes are not verified; select Ask for native permissions` для `allow`/`deny`.
- OpenCode возвращает `automatic policy requires verified OpenCode v2.1.2 and ingest`, если автоматический режим выбран, но проверенная версия/ingest недоступны.

Эти ограничения нужны, чтобы не выдавать неподтверждённое поведение за безопасное. Но сейчас общая настройка способна блокировать запуск конкретного агента, даже когда пользователь готов оставить его собственный нативный запрос разрешения.

Целевое поведение:

- В общих настройках остаются значения по умолчанию. Для каждого агента доступен режим **наследовать общие настройки** или отдельный профиль: режим запросов, обработка опасных действий и место показа запроса — только там, где адаптер это поддерживает.
- На странице разрешений видны отдельные строки Claude, Codex, OpenCode и Cursor. Для каждого агента отображаются выбранная политика, эффективное значение, источник значения (общее, профиль агента или проект), статус поддержки и проверенная версия/условия.
- Для Cursor и OpenCode должен оставаться доступен запуск в `Ask` с нативными разрешениями агента, даже если глобально выбрана автоматическая политика для других агентов. Рекомендованный профиль этих агентов — `Ask`, пока автоматические режимы не прошли проверку.
- Если пользователь явно задаёт для агента неподдерживаемый `allow`/`deny`, приложение не должно молча запускать его с более слабым режимом. До запуска оно показывает причину и предлагает выбрать поддерживаемый `Ask` или отменить запуск. Ограничивается этот агент и его политика, а не все агенты приложения.
- Приоритет общих настроек, настроек агента и проектного переопределения должен быть определён и показан пользователю до сохранения. Нельзя незаметно затереть агентский профиль общим или проектным значением.
- Миграция существующих настроек сохраняет текущие общие значения и явно показывает, какие агенты их наследуют. Для Cursor/OpenCode она должна предотвратить неожиданную блокировку запуска, не превращая `allow`/`deny` в скрытый `Ask`.

Перед сборкой исполняемого плана нужно утвердить порядок наследования и проверить матрицу режимов `ask/allow/deny` для каждого агента, включая неподтверждённые версии, отсутствие ingest и проектное переопределение. Проверки должны подтверждать как доступность нативного `Ask`, так и отсутствие незаметного обхода выбранного запрета/разрешения.

## 3. Концепция окна «Анализ проекта»

Окно должно быть рабочим пространством анализа, а не только экраном установки расширений.

### Состав окна

- **Проект и контекст:** корень проекта/worktree, Git ревизия или digest снимка, обнаруженные языки, конфигурационные файлы и уверенность обнаружения. Для нескольких языков видны все подходящие пресеты.
- **Пресет:** выбранный язык и профиль, список инструментов, версии, источник установки, обязательные системные зависимости и проверка совместимости с ОС/архитектурой. Неподдерживаемый инструмент объясняет причину и не предлагает установить его как рабочий.
- **Состояние:** `не установлен`, `устанавливается`, `готов`, `обновление доступно`, `проверка занята`, `частично доступен`, `ошибка`, `не поддерживается`. Установка, проверка и обновление показывают прогресс, отмену и понятный итог; занятость не отображается как успех.
- **Запуск:** весь проект, изменённые файлы или выбранный набор; список реальных целей анализа; возможность отменить. Для инструментов, требующих сборки, SDK, активного окружения или `compile_commands.json`, окно показывает, чего не хватает.
- **Результаты:** фильтры по инструменту, серьёзности и файлу; группировка одинаковых правил; путь, строка/столбец, код правила, сообщение, источник, уверенность и доступный fix. Карточка раскрывает минимальный фрагмент кода и причину срабатывания.
- **Полнота:** отдельно показываются охват файлов, неразрешённые файлы, ошибки запуска, таймаут, усечение и ревизия проекта. Ноль сообщений — отдельное состояние «проверка завершена, замечаний нет»; оно не используется при отсутствии подтверждения от анализатора.
- **Передача модели:** выбор набора результатов и кнопка копирования/отправки в контекст задачи. В контекст передаются также ограничения анализа и ссылки на исходные строки.

### Состояния и границы

- Снимок во время выполнения фиксируется; если проект изменился, результат маркируется устаревшим, а не прикрепляется к новому коду.
- Не запускать автоматические исправления из окна анализа без отдельного действия пользователя. Первичная цель — достоверный отчёт и управляемый вход в модель.
- Для неизвестного или недоверенного проекта нужны явное доверие и изолированный запуск. Сам факт установки расширения не означает, что проекту разрешён запуск команд.
- Экран локализуется и остаётся читаемым на узком окне. Установка и анализ не должны блокировать GTK UI.

## 4. Концепции UI для панели и окна лимитов

### 4.1 Нижняя карточка левой панели и три навигационных действия

Сейчас нижний `summary_card` объединяет лимиты аккаунтов, переход к настройкам лимитов, разделитель и три действия Plan/Index/Git. Этот блок постоянно виден рядом со списком вкладок и должен быть спроектирован как законченная часть основного рабочего процесса, а не как набор компактных кнопок.

До реализации требуется отдельно проработать назначение и иерархию блока:

- Разделить взглядом статус лимитов и навигационные действия; определить, какие сведения нужны постоянно, а какие доступны по нажатию.
- По каждой видимой учётной записи показать понятный остаток/расход, период и время сброса, предупреждение о порогах, источник и свежесть данных. Неизвестное, скрытое и устаревшее значение не маскировать нулём или «нормальным» состоянием.
- Привести три действия к понятным подписям и иерархии. Проверить, что Plan, Index и Git различимы без запоминания сокращений `IDX`/`GIT`, имеют достаточную область нажатия, accessibility label, tooltip и заметное состояние активного раздела.
- Определить поведение при отсутствии аккаунтов, скрытии всех агентов, нескольких аккаунтах, длинных именах, ошибке/задержке обновления и критическом лимите. Кнопка настройки должна появляться только с ясным смыслом и не подменять переход к подробностям.
- Сохранить место для списка вкладок: продумать, что сворачивается или сокращается при низкой высоте окна и узкой панели, не делая элементы мелкими и не перекрывая управление вкладками.
- Зафиксировать клавиатурную навигацию, порядок фокуса, состояния наведения/нажатия/выбора, светлую и тёмную темы, локализацию и увеличение системного масштаба.

Критерий готовности концепции — согласованный макет/спецификация для обычной, узкой и низкой панели и для всех перечисленных состояний данных; каждый из трёх переходов имеет проверяемый результат и ясное активное состояние.

### 4.2 Окно лимитов: пропорции, график и детализация дня

Текущий диалог задаёт ширину 850 px, фиксирует левую колонку на 245 px и растягивает правую область. График дневного расхода рисуется в области высотой 96 px; показывает stacked bars по моделям и подсказку при наведении. Пользователь не может выбрать день и раскрыть его состав. Текущая концепция должна заменить это на более качественный и читаемый обзор.

Целевой широкий макет: **левая колонка — 1/3 ширины содержимого, правая — 2/3**. Левая колонка служит устойчивым списком агентов/аккаунтов, правая — выбранному содержимому: общему обзору или подробностям выбранного аккаунта. На узкой ширине предусмотреть адаптивное представление со списком и деталями по очереди, сохраняя простой возврат к списку; не сжимать обе колонки до нечитаемого состояния.

Требования к графикам и выбору дня:

- У графика должны быть ясная временная ось, подписи дат, читаемая шкала значений, единый масштаб в пределах сравниваемых серий и легенда, согласованная с цветами моделей. Столбцы, интервалы, контраст и отступы должны оставаться различимыми на HiDPI и при системном масштабировании.
- Каждая дневная точка/колонка выбирается мышью и клавиатурой. Выбранная дата явно выделяется; рядом или в правой панели показывается декомпозиция: аккаунт/агент → модель → input, output, cache read и cache write; стоимость показывается только если её сообщил источник.
- Выбранный день синхронизируется между графиком и детализацией. Должны работать переход к соседнему дню, сброс выбора и сохранение выбранного дня при обновлении данных, если он всё ещё доступен.
- Отсутствующее наблюдение, фактический ноль и недоступная статистика — разные состояния. Отображать источник и время последнего обновления; явно отмечать частичную историю и диапазон данных.
- История идентифицирует день по UTC. В интерфейсе нужно явно выбрать и показать временную зону, чтобы дата на оси и в декомпозиции не смещалась относительно данных провайдера.
- Визуальное оформление должно давать приоритет цифрам и подписанным единицам, не полагаться только на цвет; tooltip дополняет, но не заменяет выбираемый график и постоянную детализацию.

Отдельно пересмотреть типографическую систему окна: заметный заголовок, читаемые основные числа, достаточный размер подписей/оси/легенды, согласованные межстрочные интервалы и контраст. Шрифт должен следовать настройкам GTK и системному масштабированию, корректно отображать русский и английский текст и не обрезать длинные названия моделей/аккаунтов.

До реализации утвердить макет широкого и узкого окна и таблицу состояний графика. Приёмка должна включать разные плотности данных, длинные подписи, пустую/неполную историю, большие числа, светлую/тёмную тему, HiDPI и клавиатурный выбор дня.

## 5. Где хранить расширения и проектные пресеты

### Наблюдаемое сейчас

`AnalyzerService` по умолчанию использует пользовательский каталог рядом с основной базой: `$XDG_DATA_HOME/aconsole/analyzers` или `~/.local/share/aconsole/analyzers`. В нём находятся маркер включения диагностики, каталог VSIX-расширений и управляемый host runtime. Этот путь общий для приложений пользователя. Параметр `root` в операциях диагностики задаёт worktree для анализа, а не каталог установки расширений. Отдельного манифеста закреплённых анализаторов на проект сейчас нет.

### Целевое разделение

- **Общий кэш пользователя:** проверенные неизменяемые пакеты по идентификатору, версии, платформе и SHA-256; скачивание выполняется один раз и переиспользуется разными проектами. Старые версии удаляются только после проверки, что ими не пользуется анализ.
- **Проектная декларация:** по выбору пользователя — лёгкий файл проекта с ID пресета, точными ID и версиями расширений, хэшами пакетов, версиями движков, профилем правил и минимальными требованиями. В репозиторий не кладутся VSIX, бинарники SDK и кэши.
- **Локальное состояние:** факт установки, последняя проверка, согласие на выполнение, рабочая ревизия и персональные переопределения хранятся в базе AConsole, привязанные к каноническому проекту и текущему worktree.
- **Совместимость и воспроизводимость:** установленная версия не меняется автоматически при открытии проекта. Обновление каталога и обновление выбранного проектом lock-набора — разные действия. Поддерживаются offline-кэш и явный статус «пакет недоступен в кэше».
- **Доверие:** закрытый список разрешённых расширений и зависимостей; проверка издателя, идентификатора, целевой платформы, manifest, лицензии и SHA-256; атомарная установка; ограничение прав и времени процесса; журнал источника и версии. Произвольный поиск и установка всех расширений из галереи не входят в модель.

Точный формат project manifest и возможность хранить его в репозитории — решение для исполняемого плана после выбора требований к совместной работе команды и приватности.

## 6. Предварительные языковые пресеты

Это стартовая матрица инструментов для исследования и последующей проверки совместимости. «Лучший набор» нельзя назначить по популярности: он должен совпадать с SDK и настройками проекта, а расширения — быть доступны в выбранном реестре для поддерживаемых ОС и архитектур. Для AConsole пресеты являются закрытым каталогом с ревью, а не произвольной установкой Marketplace.

| Язык | Базовая проверка и редактор | Дополнительные профили | Существенные условия |
|---|---|---|---|
| **Python** | Ruff для lint/format; Pyright для типов; обычный CLI и VS Code extension как интерфейс | Pylint — опционально для дополнительной политики и архитектурных правил; Bandit или Semgrep — профиль безопасности | Передавать `pyproject.toml`, точный Python и проектные зависимости. Не запускать Ruff и Pylint с несогласованными defaults и не считать дублирующие замечания независимым подтверждением. |
| **TypeScript/JavaScript** | `tsc --noEmit` с проектным `tsconfig`; TypeScript language service; ESLint с `typescript-eslint` и typed linting | Semgrep для выбранных правил безопасности; анализ зависимостей — отдельная capability | Типовая проверка должна использовать тот же tsconfig и тот же набор файлов, что редактор. Type-aware linting требует type information и имеет дополнительную стоимость. |
| **Rust** | rust-analyzer для IDE; `cargo check` и `cargo clippy` для проверок компилятора и lint | `cargo audit` для advisories зависимостей; Miri для тестов с `unsafe` | Miri — динамическая проверка с ограничениями, обычно требует nightly. Cargo-команды проекта могут запускать build scripts/proc macros; запуск недоверенного проекта требует изоляции и согласия. |
| **C#** | Roslyn compiler и .NET SDK analyzers как авторитетный источник; официальный C# language server как редакторский слой | Строгий профиль диагностики и Semgrep для выбранных security rules | Анализ привязывается к SDK, target framework и `EditorConfig`. Совместимость и лицензия C# extension/Dev Kit в Open VSX проверяются отдельно до включения в pin-каталог. |
| **C/C++** | clangd для IDE; компилятор и clang-tidy для compile diagnostics и lint | Clang Static Analyzer; ASan/UBSan/LSan как динамические профили | Для точного понимания проекта обычно необходима `compile_commands.json`. Санитайзеры требуют сборки и запуска; они не являются статическим линтером и не входят в обычный быстрый проход. |

### Уровни пресетов

- **Базовый:** быстрые статические и типовые проверки, минимальная настройка и понятный охват.
- **Строгий:** полный набор принятых проектом правил и предупреждений; отдельно показывает рост шума и требования к типам/SDK.
- **Безопасность:** статические security rules плюс анализ зависимостей там, где он поддерживается; каждое замечание содержит правило и доказательство.
- **Память и неопределённое поведение:** только там, где язык/сборка позволяют; включает статические проверки и явно помеченные динамические проверки/профилирование. Никакой один «плагин утечек памяти» не обещает полноту.

Профили доступны только если вся зависимость пресета поддерживается на этой платформе. Например, текущий каталог Python закреплён для Linux x64; наличие `aarch64` у host runtime ещё не означает поддержку Ruff/Pylint на ARM. UI должен считать совместимость всего набора, а не только главного расширения.

## 7. MCP-контракт и доказательная выдача модели

Существующие `analyzer_list` и `analyzer_diagnostics` — хорошее начало для Python: они связаны с worktree вкладки и сообщают ревизию, версию анализатора, запрошенные/обработанные файлы и позиции. Их не нужно заменять неограниченным `shell`.

Концептуальный набор MCP-возможностей:

1. Прочитать поддерживаемые языки, пресеты, версии, платформенные ограничения и требования запуска.
2. Получить состояние установленного набора для проекта/worktree: `installed`, `enabled`, `ready`, версии и причину недоступности — отдельные поля, не одно неоднозначное состояние.
3. Установить/обновить/удалить только разрешённый пресет или инструмент; операции ограничены allowlist, правами проекта и закреплёнными артефактами.
4. Запустить проверку заданного пресета и набора целей на конкретной ревизии; получить job ID, прогресс/отмену и итог.
5. Прочитать нормализованный отчёт страницами: код/правило, серьёзность, путь, диапазон строк, сообщение, источник, версия, конфигурация, хэш файла, ревизия, наблюдённые/непроверенные файлы, усечение и причина частичного результата.
6. Передать выбранные результаты в модель вместе с минимальным кодовым фрагментом, привязанным к той же ревизии. Модель должна различать факт от инструмента и своё объяснение; текст инструмента не переписывается как подтверждённый факт.

Статусы `полный без замечаний`, `полный с замечаниями`, `частичный`, `не запущен`, `ошибка`, `усечён` и `устарел` должны быть различимы в UI и MCP. Если расширение не умеет доказать завершение, результат остаётся `unconfirmed`; нельзя выводить «чисто» из пустого списка.

## 8. Как из концепций собрать реальный план 0.1.5

Перед созданием PlanBoard-графа:

1. Зафиксировать целевые project/worktree ID и корень, куда будет записан источник концепции и результат PlanBoard. Перед записью убедиться, что это именно копия проекта, выбранная пользователем.
2. Перепроверить замечания раздела 1 на актуальном коммите и отделить воспроизведённые дефекты от вопросов для исследования.
3. Для каждой концепции зафиксировать решение: включить в 0.1.5, отложить или отклонить — с причиной.
4. Проверить наличие расширения в выбранном реестре, лицензию, издателя, поддерживаемые версии VS Code API, ОС/архитектуру, внешние runtime и зависимости. Проверять в том числе доступность для VSCodium/Open VSX, не предполагать эквивалентность VS Marketplace.
5. Утвердить модель доверия, установки, локального/проектного хранения, версионирования и offline-поведения; отдельно согласовать наследование разрешений и совместимость режимов по агентам, особенно Cursor/OpenCode.
6. Собрать из принятых концепций граф с зависимостями: контракты, безопасность и разрешения → хранение/пресеты → запуск и доказательная модель отчёта → окно анализа проекта; отдельно спланировать переработку нижней карточки и окна лимитов → общая UI-приёмка → проверка на реальных проектах → документация и выпуск.
7. Для каждого узла указать ограниченные пути, измеримые критерии приёмки, негативные сценарии, нужные платформы и способ получения доказательства. Отдельными узлами выделить ARM/неподдерживаемые платформы, неуспешный запуск host runtime, отмену и недоверенный проект. UI-критерии должны проверять пропорцию 1/3–2/3, читаемую типографику, выбор дня и его декомпозицию, а также обычную/узкую ширину, темы, локали, HiDPI и системное масштабирование.
8. Создать новый план `AConsole 0.1.5 — анализ проектов и curated presets`; проверить его чтением через PlanBoard/MCP и сверить по тому же project/worktree ID. Не менять замороженные планы `0.1.4`.

## 9. Источники для последующей проверки

- Ruff использует конфигурацию проекта, если для extension явно не подменены настройки: [Ruff editor settings](https://docs.astral.sh/ruff/editors/settings/), [Ruff editor setup](https://docs.astral.sh/ruff/editors/setup/).
- Для Pylint в VS Code настраиваются стратегия и путь к инструменту: [Pylint extension](https://marketplace.visualstudio.com/items?itemName=ms-python.pylint).
- Pyright — самостоятельная проверка типов для Python: [Pyright configuration](https://github.com/microsoft/pyright/blob/main/docs/configuration.md), [Pyright extension](https://marketplace.visualstudio.com/items?itemName=ms-pyright.pyright).
- TypeScript даёт строгую проверку типов без генерации JS через `strict` и `noEmit`: [strict](https://www.typescriptlang.org/tsconfig/strict.html), [noEmit](https://www.typescriptlang.org/tsconfig/noEmit).
- `typescript-eslint` умеет использовать типовую информацию; согласованность TypeScript, опций компилятора и списка файлов важна: [typed linting](https://typescript-eslint.io/getting-started/typed-linting/), [troubleshooting](https://typescript-eslint.io/troubleshooting/typed-linting/).
- rust-analyzer получает diagnostics из rustc/Cargo и может использовать Clippy; Clippy отдельно запускается через Cargo: [rust-analyzer diagnostics](https://rust-analyzer.github.io/book/diagnostics.html), [Clippy usage](https://doc.rust-lang.org/stable/clippy/usage.html).
- Miri — динамическая проверка исполняемого кода, особенно относящегося к `unsafe`, и не доказывает отсутствие всех ошибок: [Rust Book: unsafe Rust and Miri](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html). `cargo audit` проверяет advisories Cargo-зависимостей: [RustSec cargo-audit](https://github.com/rustsec/rustsec/tree/main/cargo-audit).
- .NET SDK включает analyzers для code quality; настройки зависят от target framework и проекта: [.NET code analysis overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview). C# extension использует Roslyn, но для curated registry отдельно проверяются распространение и условия лицензии: [C# extension](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csharp).
- clangd требует build flags; `compile_commands.json` даёт команды компиляции для файлов: [clangd project setup](https://clangd.llvm.org/installation.html). `clang-tidy` использует compile database и настраиваемые checks: [clang-tidy](https://clang.llvm.org/extra/clang-tidy/).
- Bandit предназначен для распространённых проблем безопасности Python: [Bandit documentation](https://bandit.readthedocs.io/en/latest/). Semgrep публикует перечень поддерживаемых языков: [supported languages](https://semgrep.dev/docs/supported-languages/).
- Open VSX — отдельный открытый реестр совместимых расширений. Совместимость и доступность не следует автоматически выводить из наличия пакета в Microsoft Marketplace: [Open VSX](https://open-vsx.org/).
- Установленные расширения исполняют код; VS Code отдельно описывает доверие к издателю и ограничения Workspace Trust: [extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security), [Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust).
