# 0.1.4+g. Граф плана, индекс проекта и диагностика кода

База выпуска — 0.1.4+f, коммит `707c10ff`. Выпуск даёт человеку два интерактивных графа, а модели — поиск по всему доступному дереву проекта, чтение точных диапазонов и готовый контекст узла с результатами целевой проверки Ruff. AConsole выполняет обход, ранжирование, сбор контекста и диагностику в ядре. Модель формулирует задачу, читает подтверждающие фрагменты и принимает инженерные решения.

В 0.1.4+f есть колоночный экран плана, модульный граф, отдельные снимки worktree, компактный контекст L2 и справочник MCP. Граф корня проекта сохраняется в SQLite, отдельные рабочие копии сейчас держат индекс в памяти. Продолжение выдачи и поиск по нескольким целям входят в этот выпуск через новые методы индекса. Настройка профилей рассуждения остаётся отдельной задачей. [База выпуска](worktree-context.md)

## 1. Граф плана

Источники — существующие хранилища плана, действий исполнителя, ревью и артефактов. Проекция строится по стабильным ID узлов и ревизии плана. Снимать граф нужно согласованно с отношениями и статусами. Историю и тяжёлые поля загружать по выбранной вершине.

- В обзоре показывать направления L0 и сводку по их задачам. Раскрытие направления выводит задачи L1. Декомпозиция, зависимость и связь `related` имеют разные стили и фильтры. Для зависимостей стрелка идёт от предшественника к зависимой задаче. В хранимом контракте сохраняется существующая семантика `depends_on`. Если L0 зависит от своих L1 для закрытия, обе связи доступны отдельно.
- Локальный режим показывает выбранную вершину, её родителя, детей, ближайшие зависимости и блокируемые задачи с регулируемой глубиной. Поиск находит вершину по ключу или названию. Причины недоступности задачи показываются по данным ядра, включая незавершённые зависимости или ограничения жизненного цикла.
- Карточка L0 раскрывает цель, инварианты, ограничения, прогресс дочерних задач и результаты проверок направления. Карточка L1 раскрывает цель, пути, границы, критерии приёмки, тестовую команду, профиль проверок, требования к результату и ревью, статус, исполнителя, попытки и доступные заметки, evidence и артефакты. История результатов идёт отдельными страницами.
- Для pipeline-задачи показать шаги `spec → patch → test → verify` с состояниями известной попытки. Шаги можно раскрыть локально как элементы декомпозиции. Они сохраняют идентичность этапа конкретной попытки. Действия над ними идут через существующие операции pipeline.
- Сохранить на обычном пути все текущие действия экрана: переход во вкладку исполнителя, заморозку, ремонт контрактов и обработку ревью. При обновлении статусов сохранять выделение, масштаб и позиции. Заметка Obsidian и существующий Canvas открываются из карточки.
- Привязка к индексу строится по путям контракта и показывает заявленную область. Связь с реально изменённым файлом строится по доступному diff или артефакту с указанным источником. Обратный переход из файла показывает эти сведения с подписью подходящего типа.

## 2. Индекс проекта

### 2.1. Охват и модель данных

| Уровень | Вершины и связи | Что даёт модели |
|---|---|---|
| Проект | Пакеты и каталоги, вложенность, агрегированные межпакетные связи | Обзор подсистем, точки входа, размещение тестов, конфигурации, документации и миграций |
| Файл и модуль | Файлы дерева, модули экстракторов, принадлежность каталогу, импорты и другие связи, известные экстрактору | Точки входа, вызовы соседних компонентов на уровне модулей, связанные тесты и контракты |
| Символ | Символы, определения, диапазоны, сигнатуры и ссылки, когда их подтверждает экстрактор | Переход к точному определению и минимальному фрагменту для чтения |

- Для Git-проекта инвентарь строится по отслеживаемым и новым неигнорируемым файлам активной рабочей копии. Git-подмодуль показывается границей дерева. Для проекта без Git используется ограниченный обход с проектными исключениями. Бинарные, крупные и неподдерживаемые файлы могут иметь только метаданные. При отсутствии языкового экстрактора сохраняются инвентарь и текстовый поиск по индексируемым файлам. Обзор сообщает отдельно о покрытии файлов, символов и связей.
- Сохранить текущие ID модулей и пространство имён языков. Файл получает идентификатор из нормализованного относительного пути, символ — из языка, пути и квалифицированного имени с различителем одноимённых определений. Сдвиг строк сам по себе ID не меняет. При переименовании удалять старый ID и добавлять новый, связь с предыдущим именем показывать только при наличии данных Git.
- Использовать существующий протокол экстракторов v1 и список имён символов. Для координат и подтверждённых ссылок ввести согласованное расширение экстракторов либо отдельный дополняющий контракт. Для Python в этом выпуске обязательны диапазоны определений из AST. По остальным языкам указывать фактическое покрытие, включая модульный уровень. Типы `calls` и `references` присутствуют только при подтверждении экстрактором.
- Рёбра `contains`, `imports`, `references`, `tests` и другие поддерживаемые типы хранят источник. Связи по именованию тестов и текстовым упоминаниям имеют метку `inferred` и объяснение. Файлы с одинаковым именем и несколько модулей в одном файле возвращаются как отдельные цели, с явной привязкой к файлу.

### 2.2. Снимки, обновление и поиск

- Ключ индекса включает проект, корень worktree и версию схемы. Ревизия меняется при изменении инвентаря, индексируемого текста или координат, связей либо данных о покрытии. Обновление публикует готовый снимок атомарно. Параллельные запросы используют последний завершённый снимок, а события Git и файлов объединяются, как в существующем индексе. При исчезновении последнего снимка запрос сообщает, что индекс ещё строится.
- Применять дельты инвентаря, текста и рёбер по файлу и содержимому. Для Python повторно читать изменившиеся файлы. Для внешних экстракторов 0.1.4+g допускает перестройку затронутого языка, если его экстрактор выдаёт полный граф. При сбое языка сохранять инвентарь и результаты остальных языков. Если показываются последние успешные данные этого языка, они маркируются как устаревшие с указанием их ревизии.
- Использовать существующий подход SQLite FTS5/BM25 для текстового поиска и таблицы быстрого поиска по пути и символу. Точное совпадение идёт первым, дальше соответствие тексту и назначению запроса. Граф расширяет лучшие результаты на ограниченное число рёбер. При одинаковом ранге порядок фиксируется по типу, пути и ID. Сортировку можно воспроизвести на той же ревизии.
- Для `intent=change` поднимать определения, прямых потребителей, контракты и тесты. Для `intent=understand` поднимать точки входа, интерфейсы и документацию. Результат отдаёт причину выбора, координаты, степень подтверждения и при необходимости краткий путь связи. Неоднозначный запрос возвращает кандидатов.
- Кэшировать разбор по хэшу файла и версии анализатора, поиск — по ревизии и нормализованному запросу, результаты локальной диагностики — по эффективному профилю и хэшам входов. Рабочие копии имеют независимый цикл жизни. Вытеснение снимков и результатов ограничивается бюджетом памяти и диска, без удержания графов закрытых вкладок без срока.

## 3. Интерфейс обоих графов

Две точки входа в проекте — «План» и «Индекс». Полотно общее по механике: масштаб, перемещение, поиск, подсветка соседей, выделение и центрирование, фильтры по типам узлов и рёбер, переключение «Обзор / Окрестность». В «Индексе» есть выбор доступной рабочей копии и индикация актуальности и покрытия. По щелчку открывается карточка с путём, связями, исходником и результатами диагностики.

GTK рисует компактную сетевую карту с устойчивым расположением кластеров. Новые вершины достраиваются вокруг прежних. Раскладка вычисляется вне UI-потока, результаты устаревших запросов отбрасываются. На крупном проекте открываются агрегаты каталогов и межкластерных рёбер, а файлы и символы подгружаются при раскрытии. Подписи появляются при приближении, наведении или фокусе. Обзор, поиск и переход к вершине доступны с клавиатуры через список. На узком экране карточка открывается поверх полотна либо под ним. Цвет дублируется формой, контуром или текстом. [Обзор и локальный граф в Obsidian](https://obsidian.md/help/plugins/graph)

UI использует типизированный IPC, MCP — те же сервисы чтения ядра. Рендерер работает с компактной проекцией без непосредственного доступа к БД и исходникам. В первый кадр попадает текущая страница проекции. Раскрытие узла и переход в локальный режим запрашивают следующую часть.

## 4. MCP

### 4.1. Методы

| Метод | Вход | Ответ |
|---|---|---|
| `plan_graph` | `plan_id, mode=overview\|local, anchor?, depth?, edge_kinds?, limit?, cursor?` | Вершины с ID, ключом, статусом и готовностью, связи, счётчики свёрнутых детей, ревизия |
| `plan_node_get` | `node_id, sections?, limit?, cursor?` | Краткий статус и родитель по умолчанию. По разделам `contract`, `relations`, `attempts`, `reviews`, `artifacts` — данные соответствующего раздела и ссылки на связанные объекты |
| `index_overview` | `scope?, depth?, limit?, cursor?` | Каталоги или пакеты, счётчики, покрытие индекса, точки входа и агрегированные связи |
| `index_find` | `query, intent=understand\|change, scope?, kinds?, limit?, cursor?` | Ранжированные кандидаты, стабильные ссылки, диапазоны, причины совпадения и несколько связанных определений или тестов в том же ответе |
| `index_neighbors` | `targets, direction=in\|out\|both, edge_kinds?, depth?, limit?, cursor?` | Объединённая окрестность до восьми целей, кратчайшая цепочка до совпадения и исходная цель, покрытие, отдельно неразрешённые и неоднозначные цели |
| `index_read` | `refs, expected_revision?, max_bytes?` | Точные диапазоны или определения с фактическими координатами и хэшем файла. До восьми ссылок, статус чтения по каждой, компактное продолжение для усечённого диапазона |
| `index_task_context` | `node_id, intent=understand\|change, since_digest?, limit?` | Контракт задачи и ограничения направления, точки входа, ближайшие зависимости и тесты, рекомендуемые диапазоны, ревизия обоих графов и дайджест контекста |
| `index_lint` | `scope=changed\|node\|targets, node_id?, targets?, expected_revision?, limit?, cursor?` | Результат Ruff с кодами, позициями, компактной сводкой по файлам, хэшами входов и ссылками на файл, символ и при наличии задачу |

Все новые методы работают в контексте вкладки и доступны в режимах планирования и исполнения. `index_lint` выполняет изолированную диагностику с управляемым кэшем. Он не участвует в изменении статуса задачи. Работа с lease, fence и приёмкой идёт через существующие инструменты. `plan_get`, `plan_ready`, `step_begin`, `ctx_get` и вызов `kb_impact(target=…)` сохраняют существующую форму. `index_neighbors` реализует новый сценарий нескольких целей, используя тот же обход там, где совпадает семантика.

### 4.2. Ограничения контрактов

- Страница по умолчанию содержит до 12 элементов, максимум — 50. Общая глубина обхода 1–3, по умолчанию 1, обзор каталогов допускает глубину 0 для сводки. Основная выдача ограничена 8 КиБ JSON в UTF-8, `index_read` — 12 КиБ по умолчанию с потолком 24 КиБ. Лимит применяется к сериализованному результату с метаданными. Остаток отдаётся по курсору либо по точному диапазону. Критерии приёмки, пути и ограничения длинного контракта доступны целиком через страницы.
- Курсор непрозрачный и привязан к вкладке, ревизии, методу, каноническим параметрам и позиции. При продолжении сохраняются параметры первого запроса. Если изменился снимок или истёк срок курсора, вернуть машиночитаемую причину и предложить повторить исходный запрос. Пагинация держит стабильный порядок, без дубликатов и пропусков. Для больших разделов узла курсор также фиксирует раздел.
- В ответе индекса обязательны `revision`, `state` (`ready`, `partial`, `stale`, `building`), а при неполном покрытии — компактное пояснение. При первом построении `revision` имеет значение `null`. Ссылка включает ID либо путь и, если известны, диапазон и хэш содержимого. Перед чтением проверить соответствие источника ожидаемой ревизии и хэшу. Изменившийся файл требует повторного разрешения ссылки. Диапазоны строк включительные, с единицы. При частичном чтении вернуть результат для каждой входной ссылки в исходном порядке.
- `plan_graph(mode="local")` требует `anchor`. Направления в `index_neighbors` интерпретируются по исходному ребру. Например, для импорта `A → B` запрос `in` от `B` возвращает потребителя `A`, а `out` от `A` — зависимость `B`. Рёбра на границе страницы ссылаются на краткие объекты или помечают свёрнутый кластер. `index_lint(scope="node")` требует `node_id`, `scope="targets"` требует от одной до восьми целей, `scope="changed"` определяет цели по рабочей копии вкладки.
- В `index_task_context` дайджест учитывает эффективный контракт, доступное содержание найденных файлов и состояние результата. При совпадении `since_digest` возвращать подтверждение и актуальные ревизии. После очистки сессии модель делает запрос без дайджеста. Оперативные данные аренды остаются в ответах существующего pipeline.
- Таксономия ошибок проверяется на уровне IPC и MCP. Минимальный набор различает неизвестную цель, неоднозначность, устаревший снимок или курсор, запрещённую область, отсутствие настроенного анализатора и ошибку выполнения анализатора. Ошибки извлечения одного языка отражаются в покрытии.
- Ввод предоставляется как данные. Запросы поиска параметризованы. Проверка путей выполняется после разрешения рабочей копии, с отказом для выхода через `..`, абсолютный путь или симлинк. Источники с ограниченным доступом исключаются проектными правилами до построения выдачи и перед чтением. Кэш, курсоры и логи соблюдают те же границы вкладки и проекта.
- Методы, ограничения, примеры и доступность описываются в том же каталоге, из которого собирается справочник. Обновить типы, схему IPC, fixtures, проверку `tools/list` и сопоставление MCP с IPC. Номер API выбирать по правилам совместимости проекта после проверки добавляемых структур.

### 4.3. Примеры маршрутов

- «Где выбирается следующая задача?» → `index_find(query="plan_ready", intent="change")` возвращает MCP-вход, реализацию отбора, контракт и ближайшие тесты. `index_read` открывает нужную реализацию и тест одним вызовом.
- «Почему задача недоступна?» → `plan_node_get(sections=["relations"])` возвращает зависимости и состояние. `plan_graph(mode="local")` нужен, если блокировка продолжается через соседние задачи.
- «Изменить взятую задачу» → `plan_ready → node_claim → step_begin` для L2. Контекст поиска для активного L2 собирается тем же сервисом, что и `index_task_context`. Запрашивать отдельно его стоит для обычной задачи или углубления в индекс вне pipeline. После проверки diff `index_lint(scope="node")` собирает раннюю диагностику, штатный pipeline фиксирует итоговые доказательства.

Пример аргументов `index_read` после успешного поиска.

```json
{
  "refs": [
    {"path": "src/aconsole/core/infrastructure/mcp/server.py", "start_line": 369, "end_line": 379},
    {"path": "tests/core/test_mcp_tools.py", "start_line": 1, "end_line": 12}
  ],
  "expected_revision": "rev-from-search",
  "max_bytes": 8192
}
```

## 5. Ruff как слой графа

**Путь данных:** diff активной рабочей копии → Python-файлы → Ruff в существующей среде проверок → нормализованные диагностические записи → ссылки на индекс и узел плана.

- В `changed` брать изменённые и новые Python-файлы относительно HEAD из существующего расчёта diff. В `node` пересекать этот набор с утверждёнными путями задачи. В `targets` проверять указанные индексные ссылки. Удалённые файлы не передаются Ruff, переименованные проверяются по новому пути. Пустая область возвращает `no_targets` с нулём проверенных файлов. Для другой базы сравнения сначала использовать существующий Git-сценарий. Соседние модули показываются как контекст. Для их проверки модель или человек выбирает эти цели явно.
- Первая реализация — адаптер Ruff поверх изолированного запуска, который уже используется для проверки патчей. В запуске диагностического адаптера входной снимок монтируется для чтения, временный кэш хранится отдельно. Базовый argv формирует приложение как `ruff check --no-fix --force-exclude --output-format=json -- <files>`. Для проекта учитывается эффективная конфигурация из доступной области. MCP принимает цели и режим. Исполняемый файл, версию, параметры и ограничения определяет настроенный адаптер. Для проверки охвата использовать разрешение целей Ruff с теми же правилами исключения. Сводку можно расширить через тот же контракт для других линтеров после реализации Ruff.
- Запуск проверяет версию, разрешённые пути, профиль, лимит файлов, время выполнения и размер вывода. Включать в ключ кэша версию Ruff, канонические параметры, рабочую копию, конфигурацию с наследуемыми файлами и проверяемые версии файлов. Если вход изменился во время проверки, результат помечается устаревшим. При нормальном завершении отличать чистый результат от найденных замечаний, при сбое показывать `unavailable`, `timeout` или `tool_error`. Принудительно исключённый конфигурацией файл виден в охвате.
- Диагностика привязана к `file_id`, хэшу содержимого и диапазону. При наличии координат она получает ссылку на самый вложенный подтверждённый символ. При запросе по задаче результат также хранит её ID и область проверки. В графе видны счётчики на файле или кластере, в карточке — список замечаний и переход к строке. В карточке задачи отображать последнее состояние диагностики со временем и областью. Результат старой версии файла доступен как история.
- Сводка для модели содержит количество файлов, несколько приоритетных замечаний, коды правил и точные диапазоны. Подробности или следующие замечания выдаются по запросу. Классификация Ruff применяется как есть. Показать отдельно попадание на изменённые строки. Сортировка по изменённым строкам не влияет на полноту доступной выдачи.
- `index_lint` является ранней проверкой. Обязательные micro/blast и проектный `hostrun check` продолжают определять приёмку. Встроенные format/fix в текущем gate-профиле выполняются только через существующий конвейер и его правила. Переиспользовать результаты диагностики для отображения. Переиспользование вердикта gate допускается только через уже предусмотренный механизм кэширования этого gate.

## 6. Навыки и сценарии ядра

Навыки поставляются как короткие управляемые ресурсы AConsole. Исходники черновиков и контракт версионируются вместе. При упаковке реальные ресурсы размещаются внутри пакета AConsole, доставляются через проверенные возможности адаптера и доступны по задаче. Универсальный путь для адаптера без подтверждённой поддержки — короткая инструкция в контексте запуска и те же MCP-инструменты. Пользовательские навыки остаются под управлением пользователя. Полные схемы и инструкции загружаются только при выборе соответствующего действия.

| Навык | Когда применять | Что выполняет AConsole |
|---|---|---|
| [aconsole-project-index](../src/aconsole/skills/aconsole-project-index/SKILL.md) | Пройти от вопроса по проекту к исходному коду, тестам или влиянию правки | Индексирует, ранжирует кандидатов, разрешает ссылки, объединяет окрестности, читает запрошенные диапазоны и запускает целевой Ruff по запросу |
| [aconsole-plan-node](../src/aconsole/skills/aconsole-plan-node/SKILL.md) | Разобрать блокировку, выполнить или возобновить одну задачу плана | Собирает контракт с контекстом направления, вычисляет готовность, подбирает файлы и тесты, определяет изменённую область и диагностирует её |

Сценарии реализуются типизированными функциями ядра, которые вызывают общие сервисы напрямую. Они не выполняют последовательность MCP-вызовов от имени модели. Навык вызывает один сценарий для поиска, один для выбранного чтения и один для проверки по необходимости. Обход графа, сопоставление путей, дедупликация, подсчёт объёма, сбор diff и разбор вывода Ruff не требуют промежуточных запросов к модели. Перезапуск сценария чтения воспроизводим на одной ревизии, повтор диагностики использует только кэш совпавших входов. Выбор решения, правка кода, выбор расширенных проверок и объяснение оставшихся рисков принадлежат исполнителю.

## 8. Приёмка

Зафиксировать 12 сценариев на одной исходной ревизии. Включить поиск определения и теста, поиск одноимённых символов, изменение публичного контракта, изменение импорта, поиск документа или миграции, правку с Ruff, совпадающий путь в двух worktree, возобновление задачи и старый плоский план. Для каждого заранее указать целевые файлы, критичные связи, правильный результат и требуемые проверки.

Сравнить A — 0.1.4+f с `rg`, `kb_impact` и штатными проверками, B — 0.1.4+g с тем же набором новых MCP-методов, C — 0.1.4+g с MCP и управляемыми навыками. Для C учитывать стоимость загрузки навыка, а для всех вариантов — стоимость объявленных инструментов, доступную в измерениях CLI. Использовать одинаковую модель, рабочее состояние и настройки, минимум три повтора на сценарий, холодный и тёплый индекс считать отдельно. Для токенов использовать измерения CLI, где они доступны. Байты MCP, число поисковых вызовов, стоимость и токены кэша показывать раздельно. Отдельно измерить число операций ядра и фактических запусков Ruff, чтобы показать вклад автоматизации помимо влияния инструкций навыка.

Пороговые значения ниже являются целями выпуска. Зафиксировать их вместе с базой в G-1 до проведения сравнения.

| Критерий | Цель |
