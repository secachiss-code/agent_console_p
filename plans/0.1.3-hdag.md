## Быстрое возвращение к работе

> AConsole 0.1.3 «Детерминированный конвейер». Перевести доску планов с плоского DAG
> на трёхуровневый H-DAG: L0 — 5–8 архитектурных направлений с закреплёнными
> инвариантами, L1 — 15–25 замороженных модульных контрактов (`paths`, `acceptance`,
> `test_cmd`, radius), L2 — микро-шаги spec → patch → test → verify внутри одного узла
> L1, которые не создают вершин графа. Агент-исполнитель не видит инструментов
> изменения графа; при фундаментальном блокере он вызывает REPLAN_INTERRUPT.
> Горячее состояние конвейера живёт в `cache.db` на tmpfs, аудит и счётчики — в
> `aconsole.db`. Проверки идут каскадом: Tier 1 (линтер, типы, точечный тест,
> 0 токенов) на шаге L2.4, Tier 2 (тесты модуля и зоны влияния по рекурсивному CTE)
> при закрытии L1, Tier 3 (сквозной прогон и замеры) при закрытии L0.

**Почему сейчас.** `plan-1` начинался с 91 узла и закончился на 145: каждая недоделка
и каждый провал приёмки (QA-29…QA-36, SEC-34, SEC-35, DEBT-2) становились новой
вершиной. Это и есть разрастание плоского плана, которое H-DAG устраняет.

## 2. Решения и границы 0.1.3

Здесь зафиксированы места, где план сознательно отличается от исходной спецификации.

1. **L2 исполняет CLI-агент, ядро LLM не вызывает.** AConsole запускает Claude Code,
   Codex и др. в терминале. Ядро хранит состояние конвейера, само делает всё, что
   стоит 0 токенов (AST-срезы, хэши, проверки, конверты), и выдаёт агенту шаги через
   MCP. «Генерацию патча» и «генерацию теста» делает агент.
2. **`cache.db` не единственный источник истины.** Спецификация хранит `attempt_num`
   и `is_blocked` только в tmpfs. При перезагрузке, выходе из сеанса или повреждении
   файла (`synchronous=OFF`) счётчик обнулится, и узел получит бесконечные попытки.
   Поэтому номер попытки, статус `blocked`, цепочка `StateBlock` и квитанции проверок
   пишутся в `aconsole.db` через writer (их единицы в минуту, не десятки в секунду).
   В `cache.db` остаётся только восстановимое: scratchpad, кэш проверок, AST-скелеты,
   префиксы, трекер файлов. Потеря `cache.db` = холодный старт, не потеря данных.
   Файл нужен именно на tmpfs, а не `:memory:`: ядро выходит после 15 с простоя
   (`IDLE_EXIT_S`), и кэш должен пережить его перезапуск.
3. **Потолок `cache.db` — 64 МиБ, не 256.** Страницы tmpfs — это ОЗУ, а бюджет всего
   ядра ≤ 120 МБ. Значение настраивается; при `SQLITE_FULL` ядро вытесняет старые записи
   `verification_gate_cache` и `ast_skeleton_cache` и повторяет запись один раз.
4. **Строковый SQL по-прежнему только в `engine.py`.** PRAGMA для `cache.db` добавляются
   туда же функцией `cache_engine()`. Таблицы `cache.db` — SQLAlchemy Core на отдельной
   `MetaData` (не ORM, без Alembic), вставки — `insert().values()` с `executemany`.
   Рекурсивный CTE — `select(...).cte(recursive=True)`, `DELETE … RETURNING` —
   `delete().returning()`. Линтер не ослабляется.
5. **Схема `cache.db` версионируется `PRAGMA user_version`.** Иная версия или провал
   `PRAGMA quick_check` при открытии → файл удаляется и создаётся заново.
6. **Обход зоны влияния идёт против стрелок импорта.** В CTE спецификации обход
   `src_id → dst_id` даёт то, что *импортирует* цель, а радиусу поражения нужны те, кто
   *использует* цель: `WHERE dst_id = :target`, рекурсия по `e.dst_id = i.id`.
   `UNION` вместо `UNION ALL`: на ромбовидных графах `UNION ALL` размножает пути.
7. **`StateBlock` идентифицируется своим хэшем, без ULID и времени в хэшируемой части.**
   Иначе два одинаковых состояния дадут разные хэши, и детерминированный аудит не
   работает. Хэш — SHA-256 от `msgspec.json.encode(block, order="sorted")`.
8. **Diff не лежит в блоке.** Блок хранит `delta_ref` (`refs/aconsole/attempts/<node>/<n>/<seq>/<tree>`,
   механизм side-refs чекпоинтов) и `delta_sha256`. Полный diff не помещается в
   конверт на 200–400 токенов. Суффикс дерева сохраняет старый зелёный снимок
   при повторе шага с изменёнными файлами; ссылки не перезаписывают этот снимок.
9. **Tier 1 не «до записи на диск», а «до продвижения шага».** Агент CLI пишет файлы
   сам; честная предзапись в RAM возможна только для патчей, присланных через MCP.
   В 0.1.3: проверка идёт после записи в worktree исполнителя; при провале шаг не
   продвигается, зелёный блок не записывается, в ветку сессии ничего не попадает до
   Tier 2. Worktree не откатывается: следующая попытка продолжает накопленный diff
   (как требует сама спецификация). Агент может явно откатиться к последнему зелёному
   блоку инструментом `step_reset`. Режим предзаписи через overlay — §10.
10. **Проверки исполняются в контейнере вкладки, не на хосте.** `test_cmd`, ruff,
    basedpyright и pytest исполняют код репозитория (см. TD-SEC-7, TD-SEC-11). Ядро
    вызывает их через `podman exec` в worktree вкладки. argv берётся из профиля
    проверок L0, замороженного вместе с планом, а не из ответа агента.
11. **Бюджет Tier 1 — измеряемый, а не «15 мс + 100 мс».** basedpyright на холодном
    файле — секунды. Цель: p95 ≤ 5 с на один изменённый файл без теста, ≤ 60 с с
    точечным тестом; повтор того же состояния — 0 запусков через `verification_gate_cache`.
12. **Экономия KV-кэша — метрика, не обещание.** Порядок промпта CLI-агента задаёт сам
    CLI. AConsole гарантирует побайтово стабильные собственные части (префикс
    направления, контракт L1) и меряет долю `cache_read_input_tokens` по
    `usage_log.py`. Цель 90 % проверяется в QA-3, не постулируется.
13. **Только человек** замораживает план, применяет change request, переводит
    `blocked`/`failed` → `pending` и закрывает L0. Вкладка `mode=plan` готовит
    изменения графа, но применяются они подтверждением человека.
14. **Попытка = один проход L2.2 → L2.4.** Провал Tier 1 на L2.4 или Tier 2 при
    закрытии L1 расходует попытку. Пятая попытка не начинается: узел `blocked`,
    причина `ATTEMPTS_EXHAUSTED`, карточка в «Требует внимания».
15. **Совместимость.** Существующие планы мигрируют в `phase=frozen` (кроме
    `status=completed` — у них `phase=completed`), все узлы `level=1`, без родителя L0.
    Исключение — self-hosting `plan-636`: его `*-0` получают `level=0`. Конвейер L2
    для старых планов необязателен (флаг `pipeline` узла, по умолчанию `false` у
    старых и `true` у новых узлов из вкладки `mode=plan`). `API_VERSION` 1.4.0 → 1.5.0
    (только добавления), capability `hdag.v1`, протокол IPC остаётся 1.0.
16. **Merge не закрывает `pipeline`-узел.** `record_merge` фиксирует коммит, но не
    доказывает Tier 2. Для `pipeline=true` он переводит узел в `verifying`, снимает
    lease и пишет `plan_attention`; `done` ставит только `node_update` со свежей
    квитанцией `blast`. Узел в `verifying` после merge не возвращается в `pending`
    по таймауту: его закрывает человек или `gate_run` + `node_update`.

Вне 0.1.3: автоматический запуск цепочек агентов по DAG, предзапись через overlay,
FTS5/sqlite-vec, бюджеты API-ключей, адаптеры волн 2–4, изменение PRAGMA основной БД.

### 3.3. Граф кода в `kb_nodes`/`kb_edges` и CTE

DB-4 сохраняет результат `CodeGraphIndex` в существующие таблицы: модуль → `kb_nodes`
(`node_type=module`, id = тот же SHA-256 от `project_id\0path`, что строит
`repositories/knowledge._ref_node`), импорт → `kb_edges` (`imports`/`uses_type`/`inherits`,
`origin='codegraph'`). Так факты с `code_refs` и граф кода сходятся в одних вершинах.
Синхронизация инкрементальная: вставка новых рёбер, `delete().returning()` исчезнувших.

DB-5, эквивалент Core-выражения:

```sql
WITH RECURSIVE impact(id, depth) AS (
    SELECT src_id, 1 FROM kb_edges
     WHERE dst_id = :target AND kind IN ('imports', 'uses_type', 'inherits')
    UNION
    SELECT e.src_id, i.depth + 1
      FROM kb_edges e JOIN impact i ON e.dst_id = i.id
     WHERE i.depth < :hops AND e.kind IN ('imports', 'uses_type', 'inherits')
)
SELECT id, MIN(depth) AS depth FROM impact GROUP BY id ORDER BY depth, id LIMIT :limit;
```

Индекс `ix_kb_edges_dst (dst_id, src_id, kind)` уже покрывает этот обход.
Бюджет: ≤ 50 мс на 50 000 рёбер, 3 хопа (тест с маркером `performance`).
Если граф проекта ещё не сохранён, `kb_impact` использует нынешний обход в памяти.

## 4. Конвейер L2

### 4.1. Автомат шагов

```
           claim (lease, fence)
                 │
   ┌─────────────▼─────────────┐
   │ L2.1 spec   (ядро, 0 ток.) │  AST-срез scope + скелеты blast radius,
   │                           │  агент подтверждает affected_symbols
   └─────────────┬─────────────┘
   ┌─────────────▼─────────────┐
   │ L2.2 patch  (агент)       │  правка в worktree; ядро снимает delta_ref,
   │                           │  сверяет файлы с paths → SCOPE_VIOLATION
   └─────────────┬─────────────┘
   ┌─────────────▼─────────────┐
   │ L2.3 test   (агент)       │  тест под контракт; правка tests/ вне paths
   │                           │  → review_required
   └─────────────┬─────────────┘
   ┌─────────────▼─────────────┐
   │ L2.4 verify (ядро, Tier 1)│──FAIL──► attempt+1 ≤ max ? → L2.2 : blocked
   └─────────────┬─────────────┘
                PASS → зелёный блок → node_update(verifying) → Tier 2
                                        FAIL → attempt+1 (как выше)
                                        PASS → done / verifying (review)
```

Переходы — чистая функция в `core/domain/pipeline.py`; шаг вне порядка —
`STEP_OUT_OF_ORDER`. Ни один переход не вызывает `Plan.add`.
`record_merge` — отдельная точка: для `pipeline`-узла она не закрывает узел, а
оставляет `verifying` + `plan_attention` (см. §4.5).

### 4.2. Контракты (`src/aconsole/contracts/pipeline.py`, msgspec)

В домене — те же структуры как `@dataclass(frozen=True)`: домену msgspec запрещён.

```python
GENESIS_TAG = b"aconsole/genesis/v1\0"


class StateBlock(msgspec.Struct, frozen=True, kw_only=True, forbid_unknown_fields=True):
    v: Literal[1] = 1
    node_id: NodeId
    attempt: int                                 # 1..max_attempts
    seq: int                                     # 1..4 внутри попытки
    step_type: Literal["spec", "patch", "test", "verify"]
    prev_block_hash: str                         # первый блок: sha256(GENESIS_TAG + contract_hash)
    contract_hash: str                           # plan_nodes.contract_sha256
    delta_ref: str | None = None                 # refs/aconsole/attempts/<node>/<attempt>/<seq>
    delta_sha256: str | None = None
    diff_stat: str | None = None                 # "+12 -3, 2 files"
    affected_symbols: tuple[str, ...] = ()
    test_exit_code: int | None = None
    verification_receipt_hash: str | None = None # ставит только ядро
    token_cost_usd: float | None = None          # есть не у всех агентов


class HandoffEnvelope(msgspec.Struct, frozen=True, kw_only=True, forbid_unknown_fields=True):
    v: Literal[1] = 1
    node: str                                    # ключ, "CORE-4"
    step: Literal["spec", "patch", "test", "verify"]
    attempt: int
    max_attempts: int
    contract_hash: str
    head_block_hash: str
    scope: tuple[str, ...]                       # file_scope узла
    symbols: tuple[str, ...] = ()                # ≤ 12
    remaining_items: tuple[str, ...] = ()        # ≤ 5 × ≤ 160 символов
    compact_verdict: str | None = None           # ≤ 500 символов
    diff_stat: str | None = None
    next: str                                    # одно повелительное предложение ≤ 200
```

Конверт ≤ 1600 байт UTF-8 (≈ 400 токенов), байты считает существующий счётчик ответов
MCP. При переполнении обрезаются `remaining_items` с хвоста, затем `symbols`; `scope`
не обрезается — допуск узла ограничивает его 20 путями.

### 4.3. Хэши

- `contract_hash` = SHA-256 канонического JSON {objective, acceptance, paths, test_cmd,
  boundaries, output_format, parent L0 key, invariants L0, gate_profile L0}.
- `state_hash` = SHA-256 от: отсортированных пар (путь, `git hash-object`) файлов scope;
  хэшей скелетов blast radius; `contract_hash`; SHA-256 argv профиля проверок;
  версий инструментов в контейнере (кэшируются на вкладку).
- `receipt_hash` = SHA-256 от: `state_hash`, argv, exit code, SHA-256 stdout/stderr.

### 4.4. Раскладка контекста (Context Shaper)

Порядок ответа `step_begin` и `node_claim` — от неизменного к изменчивому:

1. префикс направления: инварианты L0, профиль проверок, публичные скелеты scope L0
   (сортировка по пути, без времени, id lease и счётчиков);
2. контракт L1: objective, acceptance, paths, test_cmd, boundaries, blast radius;
3. конверт `HandoffEnvelope`;
4. срез целевого файла (строки `start..end` вокруг `affected_symbols`).

`lease_id`, `fence`, `expires_at` — в самом конце ответа (ATT-2 из `plan-623`).
Префикс отдаётся целиком один раз за нативную сессию (`session_file_tracker`), дальше —
только `prefix_sha256`. Повтор попытки после исчерпания контекста — новая нативная
сессия с тем же первым сообщением.

### 4.5. MCP-инструменты

| Инструмент | Кто видит | Назначение |
|---|---|---|
| `step_begin(node_id, fence)` | execute, plan | ядро делает L2.1 и возвращает §4.4 |
| `step_submit(node_id, fence, step, affected_symbols?, note?)` | execute | фиксирует блок; на `verify` запускает Tier 1 |
| `step_reset(node_id, fence)` | execute | вернуть scope-файлы к последнему зелёному блоку |
| `gate_run(node_id, fence, tier)` | execute | явный запуск `micro`/`blast`, ответ — квитанция |
| `node_escalate(node_id, fence, kind, reason)` | execute | REPLAN_INTERRUPT: узел `blocked`, запись в `plan_inbox` |
| `backlog_add(plan_id, text)` | execute, plan | мысль «на потом» без вершины графа |
| `plan_create`, `plan_add_nodes`, `change_propose` | только plan | вкладка `mode=execute` их не получает в списке инструментов |

`node_update` в `verifying`/`done` для узла с `pipeline=true` требует свежую
квитанцию `blast` с `passed=1` для текущего `state_hash`; иначе `GATE_RECEIPT_REQUIRED`.
`record_merge` для `pipeline=true` не применяет `after_merge` к `done`: он оставляет
узел в `verifying`, снимает lease и пишет `plan_attention`; `done` ставит только
`node_update` с квитанцией. `node_attach kind=commit` проверяет `git rev-parse`
в worktree вкладки.

### 4.6. Коды ошибок (диапазон 4011–4019, 5008)

| Код | Имя | Когда |
|---|---|---|
| 4011 | `PLAN_FROZEN` | вставка в `frozen` без принятого change request |
| 4012 | `PLAN_ROLE` | инструмент изменения графа из вкладки `execute` |
| 4013 | `NODE_CONTRACT` | L1 без `paths`, без 1–3 пунктов `acceptance`, без `test_cmd`; `paths` вне scope L0; `blast_radius IS NULL` при наличии графа |
| 4014 | `PLAN_GROWTH_LIMIT` | `gross_added` > `baseline_nodes × 1.2`; детей у родителя > `baseline_children + 2`; глубина > 3 |
| 4015 | `SCOPE_VIOLATION` | изменённый файл вне `paths` |
| 4016 | `ATTEMPTS_EXHAUSTED` | попытка сверх `max_attempts` |
| 4017 | `STEP_OUT_OF_ORDER` | шаг L2 не по автомату |
| 4018 | `GATE_RECEIPT_REQUIRED` | закрытие L1 без зелёной квитанции Tier 2, включая `record_merge` |
| 4019 | `SPLIT_NO_PROOF` | change request `split` без квитанции, доказывающей блокер |
| 5008 | `GATE_RUNNER_UNAVAILABLE` | контейнер вкладки недоступен или инструмент не найден |

Лимиты детей и глубины считаются от baseline, а не абсолютно: у `CORE-0` в 0.1.3
шесть детей, и это легальный baseline. `baseline_children` фиксируется при заморозке;
`blast_radius = NULL` означает «граф отсутствовал», `[]` — «граф был, зависимостей
не найдено»; первое допустимо только с предупреждением, второе — легальный результат.

## 10. Задел на будущее (из общей дорожной карты)

- **Волны 2–3 (OpenCode, Cursor, Grok).** Без hooks работает рубеж (б) SEC-2 и все
  MCP-инструменты конвейера; `AgentCapabilities.pre_write_scope_guard=false` честно
  показывает отсутствие рубежа (а).
- **Волна 4 (API-ключи и бюджеты).** `StateBlock.token_cost_usd` и
  `node_attempts.cost_usd` — точка для будущего `max_cost_usd` узла и отсечки по бюджету.
- **Маршрутизация моделей, DP/Парето.** `node_attempts` (агент, модель, стоимость, исход,
  число попыток) — готовый набор данных; сам оптимизатор не входит в 0.1.3.
- **Предзапись через overlay.** `step_submit` уже принимает необязательный патч
  SEARCH/REPLACE; применение к копии в tmpfs, смонтированной в контейнер, — следующая версия.
- **FTS5 / sqlite-vec / `search_cache`.** Виртуальные таблицы создаются в миграции
  (`op.execute`; `migrations/` линтер не проверяет), запросы — в отдельном модуле с
  явным исключением в `check_no_raw_sql.py` и своим тестом.
- **PRAGMA основной БД** (`mmap_size=256 МиБ`, `wal_autocheckpoint=4000`,
  `temp_store=MEMORY`). Не принимаются без замера: отображённые страницы входят в
  RSS ядра с бюджетом 120 МБ. Кандидат на отдельный узел после QA-3.
- **Направление B (фронтенд по контракту).** Новые RPC сразу добавляются в fake core
  (`fake/results.py`, `fake/scenarios.py`), чтобы UI развивался против `aconsoled --fake`.
