# PERF-8: задержка palette/items

База: `f71469537a32a409264e552a2c9e5734d0ffef94`. Исправление — коммит, содержащий этот отчёт. Измерения выполнены последовательно на одном native-хосте, core Python 3.15.1 free-threaded, GIL выключен. Во время полных измерений другие тестовые прогоны и типизация не запускались.

## Что подтверждено

CI #43 и #44 дали первый запрос 139.909 и 141.356 мс при лимите 100 мс. Локально исходный покрытый тест воспроизводит отказ: 143.224 мс. В этом интервале GC не работал; worker потратил 15.194 мс CPU на dispatch за 129.234 мс wall time. Фоновая проекция 200 заметок шла одновременно.

Контроль на неизменной базе: первый запрос без coverage — 6.321 мс, с coverage — 132.959 мс. Пара использует одинаковый наблюдатель и исходное тело теста. Инструментация существенно меняет это измерение. Конкретный механизм накладных расходов мониторинга/планирования не установлен. Снимки ресурсов включают cgroup процесса и агрегированные root-cgroup counters; они не доказывают отсутствие ограничений во всех ancestor-cgroups.

При этом найдено два самостоятельных дефекта работы палитры:

1. `PlanBoard.node_notes` для каждой заметки заново обходил весь граф. Для 200 узлов новая регрессия фиксирует 40 200 чтений графа и падает до исправления. Общие неизменяемые данные графа теперь собираются один раз под lock; индивидуальные key/lease остаются у каждой заметки. Проверка линейного бюджета и неизменности прежних снимков после смены аренды/статуса проходит.
2. Каталог палитры запрашивал настройки через SQLite-writer, хотя не использует их. В полном прогоне без coverage наблюдался более поздний запрос 131.268 мс, из них 128.193 мс — ожидание настроек. Этот запрос лежит после первых десяти замеров исходного latency assertion; он не является отказом того assertion. Новый тест блокирует writer и воспроизводит timeout палитры до исправления. После исправления палитра получает только нужные проекты, вкладки, планы, approvals и состояние vault из памяти (`NavigationSnapshot`), а тест проходит при всё ещё заблокированном writer. Обычный `app/snapshot` сохраняет прежнюю загрузку настроек.

## Gates CI

Исходный `test_real_core_palette_route_and_latency` с теми же 200 узлами, десятью запросами, функциональными assertions и лимитом 100 мс выполняется отдельным обязательным runtime-шагом без coverage. Точное совпадение AST тела с базой проверено в `assertion-preservation.json`.

В шаге покрытия используется дополнительная выборка `not performance`. Единственный тест с этим маркером исполняется runtime-шагом; его failure делает весь workflow неуспешным. Остальные core-тесты с coverage выполняются независимо от результата runtime-шагa. Порог объединённого покрытия остаётся 90%, исходные файлы из измерения не исключаются. Это разделяет измерение времени и сбор покрытия; сырые отказы под coverage сохранены и не объявляются успешными.

Таким образом, линейная проекция и устранение SQL-зависимости не объявляются устранением накладных расходов coverage. Эти изменения проверены отдельными функциональными регрессиями.

- `regressions-before.xml`: старая проекция, линейный бюджет FAIL (40 200 > 600), остальные проверки PASS.
- `regressions-after.xml`: 8 PASS, включая граф и прежние vault-сценарии.
- `writer-before.xml`: новый сценарий занятого writer FAIL на timeout до исправления.
- `navigation-after.xml`: сценарий занятого writer PASS, весь focused-набор 13 PASS/1 instrumented-latency FAIL.
- `final-probe-smoke.xml`: архивируемые runner/plugin проверены, 1 PASS, исходный тест median 2.57 мс/max 3.70 мс.
- Ruff всего дерева PASS; strict basedpyright после окончательного изменения core PASS (0 errors/warnings/notes).

Окончательный plain-прогон: первый запрос 2.867 мс, максимум первых десяти 3.023 мс, максимум всех наблюдавшихся palette/items 3.102 мс. Полный итог: 1985 PASS, 1 штатный SKIP, 0 failures/errors, 325.193 с (`final-full-plain.xml`). CI проверяется перед приёмкой. Финальный результат workflow прикрепляется к PERF-8 в плане. QA-4 с нехваткой покрытия и PERF-7 этим этапом не закрываются.

`summary.json` разделяет первые десять измеряемых запросов и последующие обращения. Наблюдатель пишет JSON после теста, оставляет GC включённым и сохраняет исходную нагрузку. В вариантах resource чтение `/proc` добавляет небольшую накладную стоимость вокруг RPC; ранний isolated/full baseline записан до добавления этих снимков. cProfile — отдельный диагностический запуск (`candidate-profile.*`), дающий дополнительную нагрузку; его таблица на free-threaded Python содержит функции других потоков и не используется для эксклюзивной атрибуции wall time одному потоку.

## Воспроизведение

Из checkout исправления с core-окружением:

```sh
.venv-core/bin/python artifacts/perf8/runner.txt --label current-plain
.venv-core/bin/python artifacts/perf8/runner.txt --coverage --label current-covered
.venv-core/bin/python artifacts/perf8/runner.txt --full --label current-full
.venv-core/bin/python artifacts/perf8/runner.txt --regressions --coverage --functional --label functional
.venv-core/bin/python artifacts/perf8/matrix.txt
```

`matrix.txt` архивирует фиксированную базу f7146953 для isolated-контроля. Полный baseline записан в рабочем checkout этой базы до изменения продукта. Сырые покрытые измерения могут завершиться failure по исходному лимиту: это диагностический результат, а не воспроизведение обязательного uninstrumented runtime-шагa. Для повторения окончательного CI используйте команды workflow: runtime `-m performance`, coverage `-m 'not performance'`. Локальные измерения не задают верхнюю границу для произвольной внешней нагрузки или размера плана.
