# GATE-1: протокол независимой приёмки (проект, не активирован)

## Текущая граница

Ни этот документ, ни подготовленный агентом пакет не являются доверенным verifier.
`hostrun gate` остаётся диагностическим и возвращает `UNVERIFIED`; `gate-review approve`
отвергается на уровне builder и runtime, включая расширенную local policy.
Этот пакет не возвращает PASS и не меняет действующие сервисы.

Проверяющая среда пока не выделена. Обычный второй агент, другой таб, devtools
или контейнер с общим writable HOME не создают независимой границы. Само размещение
в `/opt` также её не доказывает: важны реальные mounts, credentials и доступные
агентам host-exec, Podman и systemd interfaces.

## Конкретная целевая схема

1. Независимый проверяющий получает отдельную VM либо машину, без host HOME,
   пользовательской базы AConsole, agent mounts, SSH agent, Podman/Docker sockets
   и сокета hostrun. Сетевой интерфейс приёмки допускает только передачу кандидата
   и чтение результата. Не принимает shell-команды, произвольные argv или пути.
2. Администратор среды устанавливает проверенный verifier, зависимости, policy,
   собственный набор security-тестов и baseline в каталоги, недоступные для записи
   субъекту кандидата и агентам. Фиксирует image digest и hashes до запуска.
   Исполняемый код verifier и правила нельзя импортировать из кандидата, его HOME,
   текущего каталога, PYTHONPATH, пользовательского site-packages или Git config.
3. Verifier сам создаёт одноразовый `request_id` (не менее 256 случайных бит),
   связывая его с project, task, ожидаемыми base/head/tree, полным манифестом,
   версией policy/verifier и сроком действия. Ожидаемую ревизию и область независимый
   проверяющий подтверждает по отдельному доверенному каналу. Хеш, присланный
   автором вместе с ZIP, доказывает только целостность доставки.
4. Кандидат хранится неизменяемо по digest. Извлечение выполняется в пустой каталог
   с проверкой path traversal, symlinks, hardlinks, дубликатов, типов, размеров и
   лимита распаковки. Полный список файлов и executable bits сверяется с манифестом.
   Каждый security-сценарий получает disposable worker: без host mounts, credentials,
   сети по умолчанию, привилегий и runtime socket. Checkout-код исполняется только там.
5. Независимый субъект изучает diff и логи, запускает собственные проверки и принимает
   решение по точной ревизии. Зелёный exit изменяемого кандидатом pytest/gate не служит
   независимым результатом. Субъект автора не имеет доступа к операции approval.
6. Доверенный coordinator записывает решение атомарно в append-only ledger вне worker:
   request_id, project/task, revision/tree/manifest digest, verifier/policy/image digest,
   reviewer identity, verdict, checks и hashes логов, timestamps/expiry. Worker не получает
   ключи и доступ на запись к ledger. Повтор request_id и устаревшая ревизия отвергаются.
   Для удалённой доставки нужен подписанный receipt; доверенный consumer хранит публичный
   ключ вне agent-writable HOME и одноразово потребляет request_id транзакционно.
7. PASS относится только к указанным bytes и набору проверок. При смене исходников,
   policy, verifier либо требуемой области нужен новый запрос. Проверки зависимостей
   и полный exit сохраняются; таймаут, сигнал, неизвестный exit и отсутствие security
   проверки дают отказ. Исторические FAIL не перезаписываются.

## Пакет кандидата

`prepare.py` исполняется **в агентской среде**, использует только stdlib и Git plumbing.
Читает committed blobs фиксированного HEAD, без checkout filters, export substitutions,
worktree и untracked файлов. Сохраняет executable bits; symlinks и submodules в выбранной
области отвергает. Новый каталог обязателен; существующие результаты не перезаписывает.
ZIP проверяется чтением обратно, а JSON перечисляет каждый файл, Git OID, mode и SHA256.

Пример из корня worktree:

```sh
python3 artifacts/gate1/prepare.py /tmp/aconsole-gate1-candidate-NEW
```

Для повторной передачи исторического кандидата добавьте
`--revision 2eea8a1f596b4aaa490c611f727e299efabdbb54` с новым output-каталогом.

Область указана явно в `scope`. Исторические evidence в `artifacts`, внешние docs,
runtime и незакоммиченные изменения исключены. Приёмщик должен отдельно выбрать
нужные исторические материалы и зафиксировать их hashes; отсутствие материала
нельзя объявлять успешной проверкой. Для проверки самого нового пакета нужен новый
HEAD после коммита. Сам `prepare.py` и этот документ передаются отдельно как
**недоверенные** инструкции, не устанавливаются в verifier автоматически.

## Обязательная матрица приёмки целевой системы

| Сценарий | Ожидаемый результат |
| --- | --- |
| Независимый reviewer, закреплённая ревизия, все обязательные проверки пройдены | Одноразовый PASS, полные provenance и ledger record |
| Автор вызывает approve через любую agent identity, включая подмену имени | Отказ по подтверждённой идентичности, audit record |
| Поддельный gate JSON/receipt/ключ внутри checkout или HOME | Отказ; никаких изменений доверенного ledger |
| Повтор receipt/request_id, параллельное потребление | Ровно одно потребление; остальные отказы |
| Изменение любого source/mode/tree/base/task/project/verifier/policy | Отказ без нового независимого решения |
| Истёкший запрос, отсутствие ledger/ключа/verifier, crash либо SIGTERM worker | Отказ с точным exit/диагностикой |
| Candidate код пишет в verifier, baseline, policy, ledger, ключи | Доступ запрещён на реальном worker, доказательства сохранены |
| Поддельные peer identity, socket, PATH/import/Git hooks | Нет исполнения на coordinator и нет PASS |
| Смена пакета между review и запуском | Проверяются только закреплённые immutable bytes |
| Неполная область/нет исходников/логов/обязательной проверки | Отказ, не частичный PASS |

Эти сценарии **ещё не выполнены на независимой системе**. Текущие tests/hostrun
проверяют сохранение fail-closed поведения существующей реализации, а не эту
планируемую положительную ветку. До установки и независимого прогона всей матрицы
GATE-1 остаётся незавершённым, QA-6 — failed, CMT-2 — pending.
