# UX-3 — палитра на настоящем ядре

База реализации: `dae76440`; отдельное исправление CORE-8 — `5f2f276d`.
Узел `plan-1/node-41`.

## Реализовано

Настоящий Connection маршрутизирует `palette/items`, `palette/execute` и
`palette/resetRanking` в PaletteService, подключённый Daemon. Каталог берёт
проекты/вкладки из TabService, планы из PlanBoard и запросы из ApprovalHold.
Существующая проверка IPC role/namespace выполняется до маршрутизации;
sidecar не получает доступ к новым методам.

Палитра содержит навигационные команды, вкладки, узлы планов, связанные с
ними заметки vault и ожидающие согласования. Область ограничена контекстом
проекта; неизвестный tab/project и несовпадающий контекст отклоняются.
Найденный узел открывает содержащий его план, запрос — вкладку запроса,
заметка — проверенный file URI внутри текущего vault. Обход всего диска
и индексация посторонних заметок vault не выполняются.

Выполнение заново строит актуальные цели, поэтому удалённая цель не
исполняется по старому ID. Аргументы навигационных команд запрещены;
произвольный код/команда из item_id не запускается. Рейтинг частоты хранится
в памяти процесса, ограничивается живым каталогом и сбрасывается новым
endpoint целиком либо для одного элемента. Миграция БД не требуется.

Текстовый поиск остаётся в существующем клиентском rank_items по полученному
каталогу: RPC на каждое нажатие клавиши не добавляется. Wire-контракты и UI
не менялись. `session/list` и native CLI resume остаются в HAR-3; этот коммит
не объявляет их реализованными.

## Производительность

Первый вариант пересчитывал полный read-model графа на каждом запросе.
При массовом экспорте заметок медиана достигала 60 мс, отдельные ответы —
более 180 мс. Теперь неизменяемые PlanView обновляются в кэше синхронно с
PlanBoard.on_changed; кэш заполняется и при восстановлении БД. На горячем
пути не вычисляются layout/priority/ready и сведения об агентах/лимитах.
Текущие вкладки и запросы читаются заново; note refs учитывают текущий vault.

Финальный настоящий socket-тест: **403 элемента** (200 узлов и их заметки),
10 запросов, медиана **4.87 мс**, максимум **14.66 мс**. Проверка требует
каждый ответ быстрее 100 мс. Это измерение данной локальной нагрузки,
а не гарантия для произвольного размера графа или занятого хоста.

`verification.json`, использованная конфигурация type check — рядом.

скрыта отключением watcher: устранена отдельным CORE-8 с регрессией, затем
весь перечисленный набор повторён с работающим observer.

Установленное ядро и пользовательские данные не менялись. UI/layout не
