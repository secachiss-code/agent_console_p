## Почему граф показывает только 10

Штатный read-only plan_get работающего приложения подтвердил:
{"pending": 35, "in_progress": 2, "verifying": 22, "blocked": 4, "done": 10, "failed": 2, "cancelled": 0, "total": 75}

22 узла остаются verifying с прежними ручными правилами; CORE-7 и PERF-3
числятся pending, хотя их код и обязательные проверки сохранены в main:
7152c72 и 4a487fc. Счётчик отображает сохранённый done, а не историю коммитов.
Нельзя автоматически считать все 22 проверенными: часть критериев требует
native CLI/GUI, которых полный core-набор не заменяет.

Решение пользователя kb-127: выполненное по плану с обязательными PASS должно
быть done; провал обязательной проверки — failed. Общий ручной барьер отменён.
Новая политика реализует этот порядок для дальнейшей работы.

## Изменение

Daemon явно создаёт PlanBoard(checked_completion=True). Политика передаётся
в новые планы, восстановление из store и откат после ошибки записи.
Владелец in_progress/verifying может передать done с новым evidence результатов
проверок, в том числе при старом review_required=true. Без нового evidence
завершение запрещено. Fence и владелец активной аренды продолжают проверяться.

Просроченный verifying возвращается в pending при обращении к плану, сохраняет
старое evidence, освобождает пути и требует нового claim с увеличенным fence.
Новый исполнитель повторно проверяет результат. Автоматического done по сроку
или одному старому сообщению evidence нет.

Конструкторы Plan/PlanBoard по умолчанию сохраняют ручную политику для старых
клиентов и тестов; daemon включает проверочную политику явно. Схема БД и IPC
не менялись. Ручная приёмка и роли человеческих RPC не подменялись.
Evidence — отчёт исполнителя о проверках; инструмент сам тесты не запускает
и не удостоверяет произвольный текст криптографически.
