# PERF-5: Git history frame-time diagnosis

Base commit: `95b502f583dc796a20f771ea6ce8f5157e26c922`.
`baseline.json` records SHA-256 for the unchanged test and view sources.
No application code, test body, workload, assertion or performance limit is
changed by this diagnostic node. In particular, the 10,000 commits, four-second
scroll, minimum 30 frames, median 17.5 ms and RSS growth 150 MiB limits remain.

## Findings

The failure reproduces outside the complete suite. Default `GskGLRenderer` uses
Mesa 25.2.8 llvmpipe (LLVM 20.1.2), reported as `Accelerated: no` by `glxinfo -B`
on the private Xvfb display. The process sees four CPUs with affinity 0–3.
The first isolated run starts at host load averages 3.35/3.13/2.83; these runs
are not measurements on an idle, hardware-accelerated desktop.

A controlled renderer comparison uses the identical test and application with
`GSK_RENDERER=cairo`. It improves the median from 73.5 to 30.0 ms but still fails
17.5 ms. Changing the renderer is therefore neither a sufficient fix nor a PASS.
It is evidence that the measured outcome depends substantially on the rendering
environment; the separate processes also have differing load and allocation
state, so this is not a precise subtraction of GPU cost.

There is also substantial application binding work. A **separate, profiled**
default-renderer run records 9,147 row bindings across a check with 47 scroll ticks, while
only 206 row widgets are created. Cumulative `_bind_row` time is 1.740 s;
`_show_node` accounts for 1.500 s, including 0.327 s for date formatting.
Graph snapshots account for only 0.077 s in that profile. This points to
repeated row presentation during large scroll jumps, rather than 10,000 live
widgets or graph-path Python drawing, as a useful optimization target.
The count is over the entire checked operation (loading plus scrolling).

The first unprofiled isolated run observes median scroll intervals of 73.5 ms
wall, 89.9 ms process CPU and 53.3 ms main-thread CPU. Process CPU includes
software renderer threads and can exceed wall time. Thus the observed delay
includes significant CPU work; it cannot be attributed solely to sleeping or
descheduling. These callback samples are diagnostic and differ slightly from
the benchmark's own tick boundaries; the test's report is authoritative.

The profiler measures only the current Python thread while enabled across an
async check. It includes interleaved work, instrumentation and C calls through
GI, and does not account for all native renderer work. Its times are not used
as an unprofiled benchmark or a complete frame budget.

No observed GC collection overlaps the scroll samples in either the first
isolated or the full default run. This differs from the confirmed full-GC pause
inside palette ranking fixed in PERF-6; disabling GC is not supported by this
Git-scroll evidence.

## Scope and unresolved acceptance

This node diagnoses the native-Xvfb failure; it does **not** certify smooth
scrolling or a green performance gate. The software-renderer result remains a
FAIL and must remain visible. No blanket renderer override, skipped assertion,
relaxed limit or speculative visual change is applied.

The evidence does not separate native GTK layout, Python/GI label updates,
llvmpipe work and competing host load with enough precision to claim a single
root cause for every missed frame. Hardware-accelerated results remain unknown.
The follow-up PERF-7 (`node-257`) should reduce row binding/presentation cost and measure it with
unchanged assertions, then verify on an actual accelerated desktop as well as
this reproducible software-renderer baseline. Preserve selection, badges,
localization, theme contrast and list virtualization.

## Reproduction and instrumentation

On the native host with the UI virtualenv and GTK dependencies, from this tree:

```sh
/home/sas/Projects/sp_aconsole_prototype/.venv-ui/bin/python artifacts/perf5/runner.txt --mode isolated --label repeat
/home/sas/Projects/sp_aconsole_prototype/.venv-ui/bin/python artifacts/perf5/runner.txt --mode isolated --label cairo-repeat --renderer cairo
/home/sas/Projects/sp_aconsole_prototype/.venv-ui/bin/python artifacts/perf5/runner.txt --mode isolated --label profile-repeat --profile
/home/sas/Projects/sp_aconsole_prototype/.venv-ui/bin/python artifacts/perf5/runner.txt --mode full --label full-repeat
python3 artifacts/perf5/summarize.txt
```

The runner creates/cleans its own Xvfb with Xauthority, isolated temporary XDG
state/config/cache and a real core per test. It downloads and extracts Xvfb
without installing a system package. Runs are serial; no other native test run
was launched concurrently. Ambient desktop/host load is not controlled.

`measure.py` wraps only the checked operation in the existing scale test,
records an additional lightweight tick, observes GC callbacks, and writes JSON
afterward even when the assertion fails. It does not change the collector or
thresholds. The profile run alone enables cProfile and writes a separate binary
profile plus a textual summary. `cpu.max` is unavailable at the recorded cgroup
root; the raw cgroup CPU counters are shared context and do not establish
absence of an ancestor quota or competing load.

The initial `instrumentation-error.*` run failed before the scale test body:
requesting a pytest fixture in the early setup hook was too early for the
request lifecycle. The instrumentation was moved to the call hook. That failed
attempt is preserved for transparency and excluded from measurements.
