# Снижение памяти и адаптация проверок H-DAG

Дата: 2026-11-16. Продолжение приёмки после работы над ошибками.
**UI укладывается в 150 МиБ; ядро всё ещё выше 120 МиБ. L0 не принят.**
Изменения находятся в рабочем дереве. Продуктовый plan-636 и установленный core
не менялись. Отложенный пункт 4 (глобальный Ruff baseline) не выполнялся.

## Реализовано

1. В `aconsole.ui.rendering` выбран стандартный Cairo; настройка применяется
   в `aconsole.ui.__init__` до загрузки Gtk/GDK. При Cairo отключается ненужное
   probing GL/Vulkan. Явные `GSK_RENDERER` и `GDK_DEBUG` сохраняются.
   На этой машине один только импорт Gtk загружал около 44,77 МиБ LLVM;
   `GSK_RENDERER=cairo` без отключения GDK probing почти ничего не экономил.
   Приложение остаётся GTK/VTE; рендеринг терминала и контролы не заменены.
2. Health/palette/preferences/setup/shortcuts/new-tab загружаются при первом
   обращении. Это обычные Python 3.15 `lazy from`, не глобальная политика импорта.
3. Подготовка БД вынесена в завершающийся процесс `migration_worker` до открытия
   пулов. Alembic/Mako/Pygments и ненужные SQL-диалекты не остаются в daemon.
   Проверка head, SQLite backup, миграции и retention выполняются тем же кодом,
   что раньше. Ошибка/timeout прерывают запуск. Worker использует тот же
   интерпретатор и пакет, в том числе при cwd вне checkout; GIL ядра не включается.
4. Устаревшие интеграционные тесты адаптированы к H-DAG. Graph mutations идут
   из planning-вкладки с полной парой L0/L1, затем выполняется human freeze
   через настоящий IPC до claim. Проверки 12 инструментов заменены точными
   наборами текущих capabilities, с исключением graph tools у executor.
   Проверка scope больше не требует незащищённого перехода в verifying:
   разрешённый путь не заменяет kernel receipt. Gate-правила не ослаблены.

| Сценарий | До | После |

Свежий результат и отказ закрытия с красной квитанцией:
[tier3-current.json](tier3-current.json). Ранний повтор этого этапа дал
170,46/130,01 МиБ; диапазон отражает разные процессы и состояние allocator,
а не изменение лимитов. После последнего повтора корень остаётся blocked.
Квитанция остаётся той же: kernel hash не включает сами значения метрик,
а свежий human audit сохраняет актуальные измерения.

`ui-current.json` и `core-current.json` содержат полные компонентные ряды.
Профиль UI с циклами сам считает объекты и провоцирует больший allocator high-water,
чем одиночная открытая GTK-нагрузка Tier 3; эти разные сценарии не смешиваются.
В UI после закрытия TerminalPage/TabRow не удерживаются.
Ядро по компонентному сценарию: 152,20 / 169,55 / 171,13 МиБ при пяти вкладках.
В живом Tier 3 остались реальные daemon/MCP/SQLite, пять восстановленных вкладок
и sealed runner. UI — настоящий GTK/demo с readonly IPC кандидата;
это по-прежнему не доказательство пяти одновременно работающих CLI через GUI.

Миграционный worker — **временный дополнительный процесс**, а не перенос
постоянной памяти за границу RSS ядра. Измеренный peak worker: 86,88 МиБ,
сбор новой БД около 1,98 с; `migration-peak.json`. Его память прибавляется
к памяти родителя на старте. Постоянного helper после подготовки нет.
Цена изменения — дополнительный запуск интерпретатора на старте, включая
проверку уже актуальной БД. Пиковая суммарная память старта не объявляется сниженной.

Сравнение 120 перерисовок на одном host, без отдельной фиксации CPU:

| Renderer | RSS | CPU за прогон | median frame interval | p95 |
|---|---:|---:|---:|---:|
| Cairo | 123,96 МиБ | 0,458 с | 16,78 мс | 25,16 мс |
| Явный GL | 235,02 МиБ | 0,415 с | 16,69 мс | 21,22 мс |

`ui-frames-*.json` — диагностическое сравнение, не полноценный throughput benchmark.
Cairo экономит память, но может потребовать больше CPU. Можно явно выбрать GL
через стандартный `GSK_RENDERER`; действующий RSS gate это не обходит.

## Проверка снимков

Применён `gtk-screenshot-review`. `hostrun` отсутствует; использованы эквивалентные
команды `host-spawn` с рабочим host D-Bus, установленными Gtk и `tools/ui_snapshot.py`.
Основное окно снято в отдельном Broadway: фактически 1024×768 (wide) и 700×768
(narrow). Просмотрены light/dark/narrow: видны кнопки approvals, подписи,
терминал и sidebar, raw translation keys и светлых пятен в dark нет.
На узком окне sidebar остаётся раскрытым — это воспроизводится до изменения
и совпадает с отмеченными отказами breakpoint, исправление здесь не заявляется.

Palette/preferences дополнительно сняты на host desktop: Adw.Dialog не был
mapped в Broadway. Canvas host-снимков фактически 1920×1080; эти изображения
не доказывают viewport 700×800. Одна попытка palette дала прозрачный PNG;
она сохранена отдельно как `palette-light-unmapped-attempt.png`, а канонический
light — успешный повтор с тем же исходным кодом. Временные варианты исправления
snapshot tool отклонены: захват parent-window пропускал modal, захват child
терял часть оформления. `tools/ui_snapshot.py` оставлен без изменений.
Отсутствующий `docs/design/DESIGN.md` не используется для заявления о совпадении.

## Отвергнутые эксперименты и следующий шаг

`core-imports-before.txt`, `dependency-costs.txt`, `core-heap.json` и mappings
показывают базовую стоимость зависимостей. Tracemalloc запускался отдельно:
его RSS не использован как бюджетное измерение. Исходники diagnostic probes
сохранены в `probes/*.txt`.

Глобальная lazy-политика для SDK снижала стоимость холодного импорта, но
настоящий daemon/Tier 3 дал 174,14 МиБ — устойчивого выигрыша нет.
Она **не включена** в продукт. Эксперимент следует публичному
[API Python 3.15](https://docs.python.org/3.15/library/sys.html#sys.set_lazy_imports).
`MIMALLOC_PURGE_DELAY=0` также не обеспечил нужный предел и не применён.

Оставшийся блокер — постоянная стоимость MCP/Pydantic/ORM. Следующая реализация
должна уменьшать её при активном сервере, а не только до первого запроса.
Предпочтительный следующий эксперимент: официальный low-level MCP server
вместо высокоуровневого автогенерируемого server, с сохранением аутентификации,
session pinning, схем и проверок ролей. Сначала нужен измеренный прототип и
тот же HTTP/security regression; постоянный worker вне метрики или смена
RSS на PSS не считаются решением. До свежего зелёного Tier 3 L0 остаётся blocked.

Изолированные daemon/UI, Broadway и gate-контейнер после сбора доказательств
остановлены. SQLite, fixture repository, образы и журналы сохранены; никаких
новых копий auth в этом этапе не создавалось. Handover: `ho-702`.

Последующее пользовательское решение 2026-11-16: память принята в
TD-HDG-MEM-1, основная DB-0 закрыта по human IPC (`kb-703`, plan-636: 24/29).
[Протокол](../memory-debt-closure.json). Указанное выше blocked относится
к техническому результату изолированного plan-7/ACC-0; он не переписан в PASS.
