## 1. Полный CI красный на `main` и на коммите тега — P1

**Симптом.** Все проверки GitHub Actions на `main` завершаются `failure`; последний
успешный прогон — 2026-11-03 (`fix(ui): a start that wrote nothing keeps the last real core log`).
Коммит тега `45152a1` тоже красный: шаг «Interface tests» завершился с 5 отказами.

**Данные.** Прогон `42298923032` (коммит `5f74c3cb`, тот же код, что `45152a1`):

```
5 failed, 389 passed, 1 deselected, 411 warnings in 115.32s
FAILED tests/gui/front/test_b4b_quota.py::test_the_sidebar_shows_every_window_of_an_account_shortest_first[claude-…]
FAILED …[codex-…]   FAILED …[cursor-…]   FAILED …[opencode-…]
FAILED tests/gui/front/test_clipboard_routing.py::test_real_clipboard_shortcuts[text]
```

Прогон `42364073131` (текущий `main`):

```
Core tests:       1 failed, 1847 passed, 1 skipped
Interface tests:  4 failed, 390 passed, 1 deselected
```

**Причина.** Два независимых источника:

1. `test_b4b_quota` ожидает русские подписи (`5 ч`, `7 д`, `Нед`, `Мес`) и берёт язык из
   `locale.getlocale()` (`views/sidebar/messages.py:137`), а runner CI имеет локаль `C`
   (`LC_ALL`/`LANG` не заданы) — см. п. 27.
2. `test_real_clipboard_shortcuts[text]` ожидает bracketed paste (`ESC [200~ … ESC [201~`),
   а получает сырой текст. Тот же тест нестабилен и в локальной приёмке: в
   `artifacts/git-0.1.1/VERIFICATION.md` отказ записан и успешно повторён отдельно.

**Влияние.** Зелёный CI не подтверждает ни один коммит после 2026-11-03; критерий выпуска
0.1.2 «полные core/GUI/package проверки зелёные» не выполним без исправления. Пакет 0.1.1
при этом собран и проверен локально.

**Следующий шаг.** Зафиксировать локаль в CI (`LANG`/`LC_ALL` или явная передача языка в
`translate`), стабилизировать тест bracketed paste или пометить его как средовой; проверить,
что шаги «Enforce combined coverage» и «Build and install Debian package» вообще доходят до
запуска (в красном прогоне они пропущены).

**Связанные узлы.** QA-3, QA-4, QA-6.

## 2. `test_persistence_b_tick` выходит за порог 5 мс — P1

**Симптом.** `tests/core/test_persistence_b.py::test_persistence_b_tick` падает в полном
прогоне ядра, но проходит отдельно.

**Данные.**

- Локально 2026-11-06: `p50=4.47 µs p99=10.3 µs max=6.125 мс` при пороге `5 мс`
  (`artifacts/sec10-2026-11-06/core-final.txt`).
- В CI 2026-11-07: `p50=1.63 µs p99=2.36 µs max=12.459 мс` при `n=1 448 844`.
- Пять повторов отдельно и в паре с recovery прошли; причина выброса не установлена
  (`artifacts/perf2/REPORT.md`).

**Причина.** Не установлена. Медиана и p99 далеко ниже порога, выброс — единичный; похоже
на паузу планировщика/сборки мусора в процессе теста, а не на дефект writer-очереди.

**Влияние.** Полный core-прогон красный, значит релизный критерий не выполняется. Порог и
тест не ослаблялись.

**Следующий шаг.** Измерить распределение на изолированном ядре, записать условия нагрузки
и либо подтвердить внешнюю причину документированно, либо разделить проверку на «порог
перцентилей» и «диагностический максимум» с явным решением владельца.

**Связанные узлы.** PERF-2 (`failed`), PERF-3, PERF-4.

## 3. Палитра и выбор нативной сессии не работают на настоящем ядре — P1

**Симптом.** `Ctrl+Shift+P` и выбор существующего диалога CLI работают только в демо-режиме
`--fake`. На настоящем ядре приходят `METHOD_NOT_FOUND`.

**Причина.** Методы объявлены в контрактах (`palette/items`, `palette/execute`,
`palette/resetRanking`, `session/list`), клиент UI их вызывает (`viewmodels/palette_vm.py:37`),
но в таблице обслуживаемых методов ядра (`TAB_METHODS`, `SETTINGS_METHODS`, `_APP_METHODS`,
`REVIEW_METHODS`, `GIT_METHODS`, `KNOWLEDGE_METHODS`) их нет. Это подтверждено заметкой
QA-3: «маршруты палитры и session/list отсутствуют в настоящем ядре; обязательная сверка
METHODS должна обнаруживать их».

**Влияние.** Две заявленные функции недоступны в реальной работе. Побочно недостижим
`agent --resume` для Cursor: идентификатор нативной сессии получить неоткуда, хотя ядро
умеет строить команду `agent --resume <id>`.

**Следующий шаг.** Реализовать маршруты (UX-3, HAR-3) и добавить контрактную проверку
«у каждого метода клиента есть маршрут в ядре», чтобы расхождение не повторялось.

**Связанные узлы.** UX-3, HAR-3, QA-3.

## 4. Preview и восстановление WorkSession идут по изменяемому ref — P1

**Симптом.** Если сдвинуть ref снимка после `workSession/result`, `workSession/integratePreview`
и `workSession/restore` показывают и применяют другое дерево как «тот же результат».

**Причина.** `WorkSessionSnapshot` хранит `oid`, но `WorkSessionHistory.materialize()`
получает `target.ref` (`application/services/work_session_history.py:151`), а preview
строится от `snapshot.ref`. Сверка с записанным OID появилась только в `workSession/integrate`.

**Влияние.** В ветку сессии или в рабочую копию может попасть содержимое, которого агент не
производил. Это дефект целостности данных, а не только UX.

**Состояние.** Исправлено в `main` после 0.1.1 коммитами `4c9b15a0` (GIT-1) и `0b7717f4`
(GIT-2); в опубликованный пакет не входит. Подтверждено отчётом
`artifacts/plan-reconciliation-0.1.1/REVIEW.md`.

**Следующий шаг.** Принять GIT-1 и GIT-2 в плане и выпустить в 0.1.2.

**Связанные узлы.** GIT-1, GIT-2, AUD-3.

## 5. Токен вкладки передавался в argv `podman exec` — P1

**Симптом.** `ACONSOLE_TAB_TOKEN` попадал в командную строку процесса, то есть был виден
в `/proc/<pid>/cmdline` любому процессу пользователя, включая процессы внутри контейнера.

**Причина.** `Podman.exec_spec()` формировал `-e KEY=VALUE` для всех переменных, включая
bearer вкладки; сгенерированные Claude и Codex curl-обёртки подставляли
`Authorization: Bearer $ACONSOLE_TAB_TOKEN` прямо в argv шелла (`agents/claude/launcher.py:54`,
`agents/codex/launcher.py:53`).

**Состояние.** Исправлено в `main` после 0.1.1 коммитом `d9ba7cc1` (SEC-10): Podman передаёт
`-e ACONSOLE_TAB_TOKEN` без значения, curl читает заголовок из stdin/FD 3, идентификаторы
нативных сессий валидируются, MCP проверяет Origin/Host. В 0.1.1 уязвимость **присутствует**.

**Связанные узлы.** SEC-10 (`done` в плане, но не в выпущенном пакете).

## 6. Проверка монтирования домашнего каталога отсутствует — P1

**Симптом.** Мастер и health не проверяют, смонтирован ли в контейнеры `agent-*` домашний
каталог, база `~/.local/share/aconsole`, `.bashrc` или пользовательские systemd-юниты.

**Причина.** В `HostSetupProbe.run_checks()` есть проверка монтирования worktree и vault,
но не проверка опасных монтирований. Сама AConsole монтированием не управляет.

**Влияние.** Агент с доступом к `$HOME` хоста через контейнер может изменить данные хоста,
включая собственную базу AConsole и токены. Это не эскалация привилегий (права те же), но
выход за пределы рабочей копии.

**Следующий шаг.** Предупреждение в мастере и health с рекомендуемой конфигурацией
монтирования (SEC-7).

**Связанные узлы.** SEC-7, SEC-3.

## 7. Подтверждения перед закрытием окна и вкладки нет — P1

**Симптом.** Окно и вкладка закрываются сразу, даже если агент работает или ждёт решения.

**Причина.** `views/app.py::_close_requested()` сразу скрывает окно и запускает `_finish()`,
`views/window.py::_quit()` вызывает `self.close()`. Метод `app/quitCheck` при этом
реализован и возвращает занятые вкладки и число ожидающих согласований
(`infrastructure/ipc/session.py:263`).

**Влияние.** Случайное закрытие при работающем агенте убирает сессию с экрана (снимки и
история при этом сохраняются), а ожидающие согласования исчезают без ответа — агент
останавливается на `expired_to_native` или таймауте.

**Следующий шаг.** Вызывать `app/quitCheck` из `close-request` и показывать диалог (UX-2).

**Связанные узлы.** UX-2.

## 8. Запросы Write/Edit/MCP показывают не все детали — P2

**Симптом.** В карточке согласования для `Write`, `Edit` и MCP-инструментов видны не все
поля: путь, diff и аргументы выводятся частично; длинные команды обрезаются.

**Причина.** `infrastructure/http/approval.py:52` создаёт всегда `CommandDetail(command=…,
args_preview=None)`; варианты `EditDetail` и `GenericDetail` в рабочем пути не строятся,
они есть только в fake-сценариях. `ApprovalView.summary` ограничен 4 000 символов
(`viewmodels/approvals_vm.py:10`), а карточка — 70 символами в ширину при высоте деталей
180 px (`views/approvals/panel.py:34-35`).

**Влияние.** Пользователь решает по неполным данным: не видно, какой файл и какой diff
будет применён, какие аргументы уходит в MCP-инструмент.

**Состояние после 0.1.1.** APR-2 формирует `EditDetail` для Write/Edit/MultiEdit и
`GenericDetail` для MCP. Свёрнутый предпросмотр ограничен 200 строками, все аргументы
и полный текст команд доступны по раскрытию. Пути Git, конфигов агентов и вне
worktree получают метки риска. После отключения последнего HTTP-клиента карточка
отменяется; отдельное отключение дубликата не прерывает оставшийся запрос.
Проверки и ограничения: [отчёт APR-2](artifacts/apr2/REPORT.md).

**Связанные узлы.** APR-2.

## 9. Режимов согласований «спрашивать/разрешать/запрещать» нет — P2

**Симптом.** Настраивается только место вопроса (`inline` или `native`) и время удержания.

**Причина.** В `Settings` есть `approvals_mode` (`inline`/`native`) и
`approval_hold_seconds`; режимов, подрежимов и уровней «глобально/проект» в контракте и в
ядре нет.

**Следующий шаг.** Модель режимов, адаптеры четырёх harness'ов и честная матрица в UI
(APR-4…APR-9).

**Связанные узлы.** APR-4, APR-5, APR-6, APR-7, APR-8, APR-9.

## 10. У OpenCode и Cursor нет inline-согласований и авточекпоинтов — P2

**Симптом.** Запросы этих агентов остаются нативными запросами терминала; чекпоинт перед
промптом не снимается; статус вкладки определяется по экрану sidecar'ом (тишина 1 с).

**Причина.** У обоих агентов `hooks=False`, `approvals=False`, `checkpoints=False` в
`CAPABILITIES`; `ACONSOLE_SCREEN_WATCH=1` включается только для Cursor.

**Влияние.** Матрица возможностей по агентам неоднородна, и это видно пользователю: три
агента из четырёх не дают одинакового контроля. Надёжность статусов по экрану не подтверждена
на всех CLI (HAR-4).

**Связанные узлы.** APR-6, APR-7, APR-8, HAR-4.

## 11. Часть настроек хранится, но не применяется — P2

**Симптом.** Пользователь меняет значение, оно сохраняется, поведение не меняется.

| Поле | Фактическое поведение в 0.1.1 |
|---|---|
| `notify_when` | сохраняется; уведомление о согласовании приходит при неактивном окне независимо от значения |
| `quota_warn_pct`, `quota_critical_pct` | сохраняются; уровни считаются по фиксированным 80 % и 95 % (`logic/quota_fmt.py:6-7`) |
| `codegraph_languages` | сохраняется; индексатор использует фиксированный `_LANGUAGES` |
| `checkpoints_keep` | периодическая уборка применяет значение; список в памяти ядра создаётся с умолчанием 100 |

**Причина.** Диалог настроек редактирует семь полей (`views/setup/preferences.py`), а
перечисленные выше читаются не там, где ожидается: `notify_when` используется только
`ApprovalAlerts` при неактивном окне без проверки настройки; пороги квот — константы в UI.

**Следующий шаг.** Либо применить каждое поле, либо убрать из контракта и диалога (UX-6).

**Связанные узлы.** UX-6.

## 13. Форк доступен только через API — P2

**Симптом.** В интерфейсе нет действия «форк». `tab/fork` в ядре работает и ограничен
capability `fork` (Claude, Codex), но вызывается только через типизированный фасад.

продолжает исходную нативную сессию.

## 14. Список плана обрезался до 30 узлов — P2

**Симптом.** На странице плана видно не более 30 узлов; принятые (`done`) узлы вытеснялись
из выдачи.

**Причина.** `ui/viewmodels/logic/plan_layout.py`: `SHOWN_NODES = 30`,
`_FIRST_SHOWN = (VERIFYING, IN_PROGRESS)` — сначала выбирались «ждущие», затем остальные до
лимита.

**Влияние.** Большой план (75 узлов в `plan-1`) отображался частично, счётчик расходился с
видимым. Это повлияло на восприятие состояния плана при приёмке 0.1.1.

**Состояние.** Исправлено в `main` после 0.1.1 коммитом `23a79efa` (PLAN-2):
`shown_nodes()` возвращает все узлы в порядке плана. В 0.1.1 обрезка **присутствует**.

**Связанные узлы.** PLAN-2.

## 15. `node_update` требовал fence для перехода без аренды — P2

**Симптом.** Повторить `failed`-узел через MCP было невозможно: `node_update(status=pending)`
требовал `fence: int`, а после освобождения аренды корректного fence не существует.
Domain-правила при этом допускали переход с `fence=None`.

**Причина.** `infrastructure/mcp/server.py` объявлял `fence: int` без варианта `None`
(`v0.1.1`, строки 217/227).

**Состояние.** Исправлено после 0.1.1 коммитом `7152c725` (CORE-7): `fence: int | None = None`,
heartbeat без fence по-прежнему отвергается, активная аренда проверяется по владельцу.
В работающем установленном демоне 0.1.1 поведение старое до перезапуска.

**Связанные узлы.** CORE-7, PERF-3.

## 16. Тест recovery падал из-за порядка fault injection — P2

**Симптом.** `tests/core/test_core_recovery.py::test_core_keeps_its_lock_until_a_slow_writer_has_stopped`
падал в полном наборе, но проходил отдельно.

**Причина.** Тест выставляет `writer._WAIT_S = 0.03` **до** `daemon.serve()`; параметр
используется и для ожидания постановки job в `Writer.call`, поэтому восстановление планов
не успевало за 30 мс и serve падал до открытия сокета.

**Состояние.** Диагностировано в `artifacts/perf3/REPORT.md`; исправление внесено после
0.1.1 коммитом `4a487fc3` (PERF-3) и проверено `e3a94970` (PERF-4).

**Связанные узлы.** PERF-3 (`pending`), PERF-4 (`done`).

## 21. Проверка ownership в `tools/check.sh` молча не работает — P3

**Симптом.** При заданном `HOSTRUN_CONTAINER` шаг `ownership` печатает
`warning: Not a git repository` и завершается успешно.

**Причина.** `tools/check.sh` запускает `git -C "$root" diff --name-only main...HEAD`, но в
контейнере нет ни `main`, ни доступа к нему; ошибка `git` не перехватывается как отказ.

**Влияние.** Проверка «Codex не меняет UI-файлы, Claude — core-файлы» фактически не
выполняется, но её результат засчитывается как пройденный. Это подтверждено в отчётах
`artifacts/core7/REPORT.md`, `artifacts/aud1-2026-11-06/REPORT.md`.

**Следующий шаг.** Передавать базовый коммит явно и считать любую ошибку `git` отказом
проверки (QA-4).

## 23. `tools/hostrun` и gate не принимают новые идентификаторы узлов — P3

**Симптом.** `hostrun gate CORE-7` и `gate PLAN-3` отвергаются с `gate expects a task id`.

**Причина.** `tools/hostrun/actions.py:38`: `_TASK` допускает только
`A/H/R/I/B/C` + цифры; `tools/gate/stop_gate.py:19` — только `[A-Z][0-9]{1,2}[.…]`.
Идентификаторы `CORE-7`, `PERF-3`, `SEC-10`, `GIT-1` не подходят.

**Влияние.** Для новых узлов нельзя получить штатный phase gate; в отчётах это отмечено как
известное ограничение (`artifacts/core7/REPORT.md`). Компенсируется ручными проверками.

## 24. Вспомогательный `except A, B:` вне стандарта — P3

**Симптом.** В `src/aconsole/sidecar/main.py` (строки 291 и 313) используется
`except InterruptedError, OSError, ValueError:`. Синтаксис принимается Python 3.15, но не

**Влияние.** Косметическое; на работу 0.1.1 не влияет.

**Следующий шаг.** Привести к `except (InterruptedError, OSError, ValueError):`.

## 25. Тесты GUI зависят от системной локали — P3

## 26. Ограничения, унаследованные от 0.1.0 и не исправленные в 0.1.1

| Ограничение | Влияние |
|---|---|
| Однопользовательский режим | нет серверного/multi-user развёртывания |
| Пакет только `amd64`, без GPG-подписи | нельзя ставить на других архитектурах; целостность только по SHA-256 |
| Scope файлов не изолирует параллельную запись | нужны отдельные worktree; внешние редакторы не блокируются |
| Выборочной отмены вклада агента нет | нельзя откатить один ход, не откатывая чекпоинт целиком |
| Автоматического запуска цепочек по DAG нет | план — доска, а не оркестратор |
| `AConsole` не создаёт контейнеры и не логинит CLI | мастер только сообщает, что сделать |
| Cursor и OpenCode используют непубличные endpoint'ы лимитов | формат может измениться без предупреждения |
| Поддержка вложений PNG подтверждена только в Codex | в Cursor путь остаётся текстом; Claude и OpenCode не проверялись |
